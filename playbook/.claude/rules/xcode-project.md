# Xcode project, lockfiles, plists, entitlements

<!-- composed: not from official docs; policy adapted from tomada1114/ios-template .claude/rules/project.md, Apple's CI guidance on Package.resolved, and the practitioner consensus that agents are weak at project-file edits (research notes). Validate in your repo. -->

Reminder: this rule loads only when such a file is Read/Written/Edited, which is too late to prevent an edit. The
hard stops are `.claude/settings.json` deny rules (`Edit(**/*.pbxproj)`, lockfiles, entitlements) and
`.claude/hooks/protect-files.sh` (exit 2 on PreToolUse). Do not try to work around them.

## `project.pbxproj`, `*.xcworkspacedata`

- NEVER hand-edit. If the project is generated: edit `project.yml` (XcodeGen) or `Project.swift` (Tuist) and run `xcodegen generate` / `tuist generate`. If it is not generated: describe the change (target, file, build setting) and ask the user to make it in Xcode, or ask for the generated-project migration.
- Adding a file to a target in a non-generated project: Xcode 16+ synchronized folders pick up new files automatically; if the target uses classic groups, ask.

## Lockfiles: `Podfile.lock`, `Package.resolved`

- Never edit by hand. They are regenerated by the tool: `pod install` (asks), `xcodebuild -resolvePackageDependencies`, `swift package resolve`. A lockfile diff is only acceptable together with an approved dependency change (CLAUDE.md > Needs human sign-off).
- CI and `scripts/xcb.sh` pass `-disableAutomaticPackageResolution` when `XCB_NO_PACKAGE_RESOLUTION=1`, so a stale `Package.resolved` fails the build instead of silently bumping versions. Commit `Package.resolved` (for an app it lives under `*.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/`).
- CocoaPods projects build through the `.xcworkspace`; `pod install --deployment` refuses any lockfile change (use it in CI); "Spec not found" (exit 31) means `pod install --repo-update`.

## `Info.plist`, `*.xctestplan`, `project.yml`, `Project.swift`, `*.xcconfig`

- Editable, but every key you add must be justified in the PR description. Privacy usage strings (`NS*UsageDescription`) need the actual user-facing wording from the product owner.
- Version and build numbers: never edit `CFBundleShortVersionString`/`CFBundleVersion` or `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` by hand; use `/release-check` (agvtool) with approval.
- Never move a build setting from an `.xcconfig` into the pbxproj.

## `*.entitlements`, signing, provisioning

- Read-only for Claude. Capabilities, App Groups, Associated Domains, signing identities and profiles need human sign-off and are changed in Xcode by a person. Propose the exact key and value in prose.
