## 1. Headless builds and tests: exact `xcodebuild` invocations, keeping output small, extracting results from `.xcresult`, SwiftPM and Swift tooling

### Takeaway
The canonical headless loop is `xcodebuild -workspace|-project … -scheme … -destination 'platform=iOS Simulator,name=…' -derivedDataPath … -resultBundlePath … -quiet build|test`, with `-only-testing:Target/Class/method` to narrow tests, then `xcrun xcresulttool get test-results summary --path X.xcresult --compact` (Xcode 16+ syntax; the old `get --format json` form now errors unless `--legacy` is passed). For context economy pipe through `xcbeautify --quiet`/`-qq` (or the agent-oriented `xcsift`), and remember Claude Code itself truncates MCP tool output above 25,000 tokens by default.

#### `xcodebuild` option semantics (verbatim from the man page; note the mirror's body is dated 2016 and lacks the SwiftPM flags, see §3)
- `-list` — "Lists the targets and configurations in a project, or the schemes in a workspace. Does not initiate a build. Use with -project or -workspace." — [xcodebuild(1) man page mirror (keith/xcode-man-pages)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-showdestinations` — "Lists the valid destinations for a project or workspace and scheme. Does not initiate a build. Use with -project or -workspace and -scheme." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-showBuildSettings` — "Lists the build settings for targets in a project or workspace. Does not initiate a build. Use with -target or with -scheme. With -scheme, optionally pass a build action (such as build or test) to use targets from the matching scheme action." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-showsdks` — "Lists all available SDKs that Xcode knows about, including their canonical names suitable for use with -sdk." ; `-showTestPlans` — "Lists the test plans (if any) associated with the specified scheme." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-destination destinationspecifier` — "Use the destination device described by destinationspecifier. Defaults to a destination that is compatible with the selected scheme." `-destination-timeout timeout` — "Use the specified timeout when searching for a destination device. The default is 30 seconds." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-only-testing` / `-skip-testing`: "Test identifiers have the form TestTarget[/TestClass[/TestMethod]]. The TestTarget component of an identifier is the name of a unit or UI testing [bundle]…" `-only-testing constrains a test action to only testing a specified identifier, and excluding all other identifiers.` — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-resultBundlePath path` — "Writes a bundle to the specified path with results from performing an action on a scheme in a workspace. If the path already exists, xcodebuild will exit with an error. Intermediate directories will be created automatically. The bundle contains build logs, code coverage reports, XML property lists with test results, screenshots and other attachments collected during testing, and various diagnostic logs." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-derivedDataPath path` — "Overrides the folder that should be used for derived data when performing an action on a scheme in a workspace." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-quiet` — "Do not print any output except for warnings and errors." `-verbose` — "Provide additional status output." — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)
- `-parallel-testing-enabled [YES | NO]` — "Overrides the per-target setting in the scheme for running tests in parallel."; `-parallel-testing-worker-count number`; `-testPlan test-plan-name` — "Pass the name of the .xctestplan file without its extension."; `-test-timeouts-enabled [YES | NO]`; `-default-test-execution-time-allowance seconds`; `-maximum-test-execution-time-allowance seconds`; `-test-iterations number` with `-retry-tests-on-failure` / `-run-tests-until-failure`; `-collect-test-diagnostics [on-failure | never]`; `-enableCodeCoverage [YES | NO]`; `-skipUnavailableActions` — "Skip actions that cannot be performed instead of failing. - Actions: `build-for-testing` — "Build the target and associated tests in the build root (SYMROOT). This will also produce an xctestrun file in the build root. This requires specifying a scheme."; `test-without-building` — "Test compiled bundles. If a scheme is provided with -scheme then the command finds bundles in the build root (SRCROOT). - `-allowProvisioningUpdates` — "Allow xcodebuild to communicate with the Apple Developer website. - Man-page examples (verbatim): `xcodebuild build-for-testing -workspace MyWorkspace.xcworkspace -scheme MyScheme -destination generic/platform=iOS`; `xcodebuild test-without-building -workspace MyWorkspace.xcworkspace -scheme MyScheme -destination 'platform=iOS Simulator,name=iPhone 5s' -destination 'platform=iOS,name=My iPad'`; `xcodebuild test -workspace MyWorkspace.xcworkspace -scheme MyScheme -destination 'platform=macOS,arch=x86_64' -only-testing MyTests/FooTests/testFooWithBar` — [xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)

### Inferences
- A copy-paste iPhone test command consistent with the sources above: `set -o pipefail; NSUnbufferedIO=YES xcodebuild test -workspace App.xcworkspace -scheme App -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath ./.derivedData -resultBundlePath ./build/App.xcresult -quiet -only-testing:AppTests/LoginTests 2>&1 | xcbeautify -qq --is-ci`; for Apple TV swap `-destination 'platform=tvOS Simulator,name=Apple TV 4K (3rd generation)'` (or `generic/platform=tvOS Simulator` for build-only). Because `-resultBundlePath` errors if the path exists, agents should `rm -rf` the bundle first.
- The post-run extraction sequence is `xcrun xcresulttool get test-results summary --path ./build/App.xcresult --compact`, then `get test-results tests` to find `testIdentifier`s, then `get test-results test-details --test-id <id>` and `export attachments --only-failures` for screenshots; `get log --type console` replaces the old `export … --id <logRef>` dance.
- For an agent loop, `build-for-testing` once + repeated `test-without-building -xctestrun … -only-testing:…` is the cheapest way to re-run a single failing test without recompiling.

### Gaps
- `xcodebuild -list -json` / `-showdestinations -json` output format: no primary Apple source was retrievable (the man-page mirror body is from 2016); verify with `xcodebuild -help` on the target machine.
- Apple does not publish a web page for `xcresulttool`; the man page above is the authoritative text, but the JSON schemas are only available via `xcrun xcresulttool help get test-results <subcommand>`.
- xcpretty's maintenance status could not be confirmed (README shows no notice and the Releases list appeared empty in the fetch).
- `swift-format` exit codes and `swift package resolve --skip-update` behaviour were not documented on fetched pages.

## 2. Simulator control: `xcrun simctl`, idb, tvOS input, screenshots for agent verification

### Takeaway

## 3. CocoaPods and SPM in agent loops: workspace vs project, resolution flags, caching, typical failures

### Takeaway
Commit `Package.resolved` and run `xcodebuild … -disableAutomaticPackageResolution` (Apple's own CI guidance) so an agent never silently bumps dependencies; add `-skipMacroValidation`/`-skipPackagePluginValidation` for macro/plugin projects (MobileBuildMCP passes the former by default), and keep SwiftPM checkouts in a hidden or out-of-tree `-clonedSourcePackagesDirPath`. CocoaPods projects must be built through the `.xcworkspace`; `pod install --repo-update` forces a specs update and `--deployment` refuses any Podfile.lock change.

### Cited Findings
- Apple: "be sure to commit your project's `Package.resolved` file to your Git repository… You can find the `Package.resolved` file inside your `.xcodeproj` directory at *[appName]*`.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`. If your CI pipeline uses the `xcodebuild` command directly, also pass the `-disableAutomaticPackageResolution` flag. This flag ensures that the CI pipeline always uses the package dependencies as defined in the `Package.resolved` file."; "To have `xcodebuild` use your Mac's Git installation and configuration, pass `-scmProvider system`"; private packages: use SSH URLs and set up `~/.ssh/known_hosts` for the CI user — [Building Swift packages or apps that use them in CI workflows](https://developer.apple.com/documentation/xcode/building-swift-packages-or-apps-that-use-them-in-continuous-integration-workflows)
- SwiftPM's own CI doc repeats `-scmProvider system` and states "Package manager honors the machine's SSH configuration" — [ContinuousIntegration.md](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/PackageManagerDocs/Documentation.docc/ContinuousIntegration.md)

### Inferences
- Pattern for an agent's CLAUDE.md: `xcodebuild -workspace App.xcworkspace -scheme App -destination '…' -derivedDataPath ./.derivedData -clonedSourcePackagesDirPath ./.spm -disableAutomaticPackageResolution -skipPackagePluginValidation -skipMacroValidation -quiet build` with `.derivedData`/`.spm` git-ignored; run `xcodebuild -resolvePackageDependencies …` only when `Package.resolved` changed.
- Diagnostics the agent should recognize: "Spec not found" (exit 31) → `pod install --repo-update`; Podfile.lock drift under `--deployment` → regenerate locally, never on CI; "plugin must be enabled/trusted" → `-skipPackagePluginValidation`; macro validation errors → `-skipMacroValidation`; build-for-testing with plugins + multiple `-destination` → split into per-destination invocations.

### Gaps
- The CocoaPods guides site (semantics of `pod install` vs `pod update`, `pod deintegrate`) was unreachable; only the CLI source was read.
- Apple has no public reference for `-skipPackagePluginValidation`/`-skipMacroValidation`; their existence is evidenced by tool source and forum posts, not an Apple doc.
- Tuist's CLI/MCP docs and Tuist cache commands could not be fetched; cited from search summaries only.

## 4. MCP servers and plugins for Xcode; Xcode 26.3/27 agent integration vs CLI workflows

### Takeaway

## 5. tvOS specifics: focus-engine debugging, driving and verifying focus, XCUIRemote, TVUIKit, Top Shelf, build/destination gotchas

### Takeaway
Apple's two official focus-debugging tools are the `-UIFocusLoggingEnabled YES` launch argument and the `UIFocusDebugger` lldb class (`po UIFocusDebugger.status()`, `checkFocusability(for:)`, `simulateFocusUpdateRequest(from:)`, `focusGroups(for:)`, `preferredFocusEnvironments(for:)`, `help()`); `UIFocusGuide`/`preferredFocusEnvironments` fix dead zones in UIKit and `focusSection()`/`@FocusState` in SwiftUI. UI tests drive the remote with `XCUIRemote.shared.press(.select)` and the simulator is driven with arrow/Return/Escape keys; an agent verifies focus from the accessibility tree plus a screenshot, or by running `po UIFocusDebugger.status()` through an attached lldb.

### Cited Findings

#### Apple focus debugging APIs
- "To help you find focus problems, Apple provides two debugging tools: `UIFocusLoggingEnabled` and `UIFocusDebugger`." Enable logging: "select Edit Scheme and add `-UIFocusLoggingEnabled YES` to the Arguments Passed On Launch section… the debugger logs all focus events and displays the events in the Xcode console and the Console app." Example: "`po UIFocusDebugger.status()` returns the state of the focus engine." — [Debugging focus issues in your app](https://developer.apple.com/documentation/uikit/debugging-focus-issues-in-your-app)
- `@MainActor class UIFocusDebugger` (tvOS 11.0+, iOS 11.0+): "You do not use this class or its methods directly from your code. During a debugging session, you can call the methods of this class from the `lldb` debugger command line"; methods `class func help() -> any UIFocusDebuggerOutput`, `status()`, `checkFocusability(for: any UIFocusItem)` ("Returns information about whether the item can become focused, including any known issues that would prevent the item from becoming focused."), `focusGroups(for: any UIFocusEnvironment)`, `preferredFocusEnvironments(for: any UIFocusEnvironment)`, `simulateFocusUpdateRequest(from: any UIFocusEnvironment)` ("Simulates a focus update request from the specified environment.") — [UIFocusDebugger](https://developer.apple.com/documentation/uikit/uifocusdebugger)
- `simulateFocusUpdateRequest(from:)` "simulates a focus update request, outlining each step of the process for determining the next focused item"; Objective-C lldb form for focusability: `po [UIFocusDebugger checkFocusabilityForItem: item]` (search summary of Apple symbol pages) — [UIFocusDebugger.simulateFocusUpdateRequest(from:)](https://developer.apple.com/documentation/uikit/uifocusdebugger/simulatefocusupdaterequest(from:)), [checkFocusability(for:)](https://developer.apple.com/documentation/uikit/uifocusdebugger/checkfocusability(for:))
- Real `checkFocusability()` output: `<UIFocusUpdateContext: 0x600003318000: previouslyFocusedItem=<FV: 0x102a17f30>, nextFocusedItem=(null), focusHeading=Down>` then `The following issues were found that would prevent this item from being focusable: - ISSUE: This item is not visible onscreen.`; root cause was a zero-frame `UIView` in a second `UIWindow` (no Auto Layout), fixed by giving it a size — [Apple Developer Forums thread 751311](https://developer.apple.com/forums/thread/751311)
- Focus engine rules: "Only the focus engine can explicitly update focus, meaning there's no API for directly setting the focused item or moving focus in a particular direction."; "If no element is found in that direction, the currently focused item stays in focus and a `movementDidFailNotification` notification is broadcast."; "The root view controller's `preferredFocusEnvironments` property is the first focus environment that's selected to gain focus."; use `canBecomeFocused` to know if an item is focusable — [About focus interactions for Apple TV](https://developer.apple.com/documentation/uikit/about-focus-interactions-for-apple-tv)
- `UIFocusGuide` (tvOS 9+): "an invisible, focusable region that can redirect focus movement to other views"; properties `isEnabled`, `preferredFocusEnvironments: [any UIFocusEnvironment]!` ("ordered by priority"), `preferredFocusedView` — [UIFocusGuide](https://developer.apple.com/documentation/uikit/uifocusguide)
- `UIFocusUpdateContext` (tvOS 9+): `previouslyFocusedView`, `nextFocusedView`, `focusHeading: UIFocusHeading`, `previouslyFocusedItem`, `nextFocusedItem`; notifications `UIFocusSystem.didUpdateNotification`, `movementDidFailNotification`, user-info keys `animationCoordinatorUserInfoKey`, `focusUpdateContextUserInfoKey` — [UIFocusUpdateContext](https://developer.apple.com/documentation/uikit/uifocusupdatecontext)
- SwiftUI `focusSection()` (tvOS 15+, macOS 13+): "Indicates that the view's frame and cohort of focusable descendants should be used to guide focus movement"; the doc's tvOS example makes a right-hand `VStack` reachable by swiping right from buttons 1–3; "`focusSection()` does not affect the focusability of the modified view. If the modified view has no focusable descendants, then the modifier does nothing." — [focusSection()](https://developer.apple.com/documentation/swiftui/view/focussection())
- SwiftUI `focusable(_ isFocusable: Bool = true, interactions: FocusInteractions)` (tvOS 17+); `MyTapGestureView(...).focusable(interactions: .activate)` — [focusable(_:interactions:)](https://developer.apple.com/documentation/swiftui/view/focusable(_:interactions:))
- `@FocusState` (tvOS 15+): use with `focused(_:equals:)`/`focused(_:)`; "Setting the property's value programmatically has the reverse effect, causing focus to move to the view associated with the updated value"; wrapped value must be optional or Bool; `focused(_:)` on a container reports true when a descendant has focus, `focused(_:equals:)` distinguishes container vs field — [FocusState](https://developer.apple.com/documentation/swiftui/focusstate)

### Inferences
- A non-interactive focus probe an agent can run: build Debug, launch in the simulator, then `xcrun lldb --batch -o "process attach --name MyTVApp" -o "expr -l Swift -- import UIKit" -o "po UIFocusDebugger.status()" -o "process detach"` (lldb flags from §6; the Swift `import` step is an inference—`po UIFocusDebugger.status()` is Apple's documented form inside an Xcode session).
- Pair `-UIFocusLoggingEnabled YES` with `simctl launch --console-pty` or `simctl spawn … log stream` to capture focus-engine logs headlessly; `movementDidFailNotification` observers can log "focus dead ends" into os_log for the same stream.
- In SwiftUI-on-tvOS, most "can't reach that button" bugs are missing `focusSection()` on the container, mirroring `UIFocusGuide` in UIKit.

## 6. Debugging headlessly: lldb batch mode, crash symbolication, unified logging, Instruments CLI, and feeding results to Claude

### Takeaway
Use `lldb --batch -o/-s` (or `-p/-n/-w` to attach) for scripted debugger sessions; symbolicate `.ips`/`.crash` files with Apple's `xcrun crashlog <file>`, `CrashSymbolicator.py -d App.dSYM`, or `atos -arch arm64 -o App.app.dSYM/Contents/Resources/DWARF/App -l <load> -i <addr>`; read logs with `log stream --predicate 'subsystem == "…"'` (through `xcrun simctl spawn <udid> log stream …` for simulators); profile with `xcrun xctrace record --template 'Time Profiler' … --launch -- App.app` and `xctrace export --toc/--xpath`. Keep what reaches Claude small: `--compact` JSON, `--only-failures` attachments, predicate-filtered logs, and XPath-filtered trace exports.

### Cited Findings

#### lldb non-interactive
- `--batch` / `-b`: "Tells the debugger to run the commands from -s, -S, -o & -O, and then quit."; `--one-line <command>` / `-o`: "execute this one-line lldb command after any file provided on the command line has been loaded."; `--one-line-before-file` / `-O`; `--source <file>` / `-s`; `--source-before-file` / `-S`; `--one-line-on-crash` / `-k`: "When in batch mode, tells the debugger to run this one-line lldb command if the target crashes."; `--source-on-crash` / `-K`; `--attach-pid <pid>` / `-p`; `--attach-name <name>` / `-n`; `--wait-for` / `-w`: "wait for a process with the given pid or name to launch before attaching."; `--source-quietly` / `-Q` — [lldb(1) man page mirror](https://keith.github.io/xcode-man-pages/lldb.1.html)
- Xcode 27 LLDB: "LLDB now ships with an MCP server (lldb-mcp)"; new `language swift task tree` command; faster first `po` with bridging headers — [Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)

#### Crash symbolication (Apple, current)
- "Crash reports must have the `.crash` or `.ips` file extension. If the file has a different extension or no extension, rename the file before symbolicating."; Xcode symbolicates on open — [Adding identifiable symbol names to a crash report](https://developer.apple.com/documentation/xcode/adding-identifiable-symbol-names-to-a-crash-report)
- CLI: `xcrun crashlog <path-to-crashReport>` ("a shortcut to invoke a Python module that supports parsing and symbolicating crash reports. The module installs `crashlog` into the LLDB command interpreter"); inside lldb: `(lldb) command script import lldb.macosx.crashlog` then `(lldb) crashlog /Users/.../TouchCanvas.ips`; `xcrun crashlog --help` — [same Apple doc](https://developer.apple.com/documentation/xcode/adding-identifiable-symbol-names-to-a-crash-report)
- Script: `cd /Applications/Xcode.app/Contents/SharedFrameworks/CoreSymbolicationDT.framework/Resources` then `python3 CrashSymbolicator.py <path-to-crashReport> -d <path-to-dSYM>` ("supports JSON-format crash reports and inlined frames"), `-o <output.ips>` to save — [same Apple doc](https://developer.apple.com/documentation/xcode/adding-identifiable-symbol-names-to-a-crash-report)
- `atos -arch <binary-architecture> -o <path-to-dSYM>/Contents/Resources/DWARF/<binary-name> [-l <load-address>] [-textExecAddress <address>] [-i] [-dedup] <addresses-to-symbolicate>`; example `atos -arch arm64 -o TouchCanvas.app.dSYM/Contents/Resources/DWARF/TouchCanvas -l 0x10459c000 -i 0x1045a4610` → `@objc ViewController.touchesEstimatedPropertiesUpdated(_:) (in TouchCanvas) (/<compiler-generated>:0)`; `-i` reveals inlined frames; `-dedup` expands `<deduplicated_symbol>`; "provide the path to this file, not just to the `.dSYM` bundle" — [same Apple doc](https://developer.apple.com/documentation/xcode/adding-identifiable-symbol-names-to-a-crash-report)
- Developers report the Devices window "Device Logs" button is gone in Xcode 15.1 and `atos` is the fallback when Xcode leaves addresses unsymbolicated; match dSYM with `dwarfdump --uuid` — [Apple Developer Forums 745947](https://developer.apple.com/forums/thread/745947), [740153](https://developer.apple.com/forums/thread/740153), [767800](https://developer.apple.com/forums/thread/767800)

### Inferences
- A headless crash triage recipe: locate `.ips` under `~/Library/Logs/DiagnosticReports` (device) or the simulator's container, run `xcrun crashlog <file>` first (needs the matching dSYM discoverable by Spotlight), and fall back to `atos` for single frames; pipe only the crashed thread into Claude.
- `xctrace record … --device "Apple TV 4K (3rd generation) simulator"` form follows the man page's "if the word simulator is included" rule; pre-Xcode-27 simulator recordings may silently produce nothing (fixed in 27).
