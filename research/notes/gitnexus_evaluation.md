## Key Question 1: What exactly is GitNexus and how does it work (architecture, indexing, graph, MCP, skills)?

### Takeaway
GitNexus is an npm-distributed CLI + MCP server (plus a browser WASM UI) that parses a repo with Tree-sitter into a knowledge graph stored in an embedded graph DB (LadybugDB), precomputes clusters (Leiden community detection), execution "processes," and hybrid search indexes, and then exposes 19 MCP tools (`query`, `context`, `impact`, `trace`, `detect_changes`, `cypher`, etc.), MCP resources, skills, and Claude Code hooks so an agent gets structural context in one tool call. The "zero-server" phrase refers to the browser UI; the recommended CLI/MCP path is a local Node process.

### Cited Findings
- GitHub "About" description: "GitNexus: The Zero-Server Code Intelligence Engine"; README tagline: "The context engine for Enterprise Codebases" — [GitHub repo page](https://github.com/abhigyanpatwari/GitNexus)
- README one-liner: "Indexes any codebase into a knowledge graph — every dependency, call chain, cluster, and execution flow — then exposes it through smart MCP tools so AI agents never miss code." — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- README TL;DR: "The **CLI + MCP** makes your AI agent reliable — it gives Cursor, Claude Code, Antigravity, Codex, and friends a deep architectural view of your codebase so they stop missing dependencies, breaking call chains, and shipping blind edits. Even smaller models get full architectural clarity. The **Web UI** is a quick way to chat with any repo in the browser." — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- README "How It Works" (verbatim pipeline): "1. **Structure** — walks the file tree and maps folder/file relationships 2. **Parsing** — extracts functions, classes, methods, and interfaces using Tree-sitter ASTs 3. **Resolution** — resolves imports, function calls, heritage, constructor inference, and `self`/`this` receiver types across files with language-aware logic 4. **Clustering** — groups related symbols into functional communities 5. **Processes** — traces execution flows from entry points through call chains 6. **Search** — builds hybrid search indexes for fast retrieval" — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- README "Core innovation: Precomputed Relational Intelligence": "**Reliability** — the LLM can't miss context; it's already in the tool response · **Token efficiency** — no 10-query chains to understand one function · **Model democratization** — smaller LLMs work because the tools do the heavy lifting" (these are vendor claims, no numbers attached in the README) — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Two deployment modes per README table: CLI+MCP uses "Tree-sitter native bindings" and LadybugDB native storage; Web UI uses "Tree-sitter WASM" and LadybugDB WASM, limited by browser memory (~5k files); `gitnexus serve` bridges the two. "The web UI uses the same indexing pipeline as the CLI but runs entirely in WebAssembly (Tree-sitter WASM, LadybugDB WASM, in-browser embeddings)." — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- ARCHITECTURE.md: "The default DAG of 19 phases builds a `KnowledgeGraph` in memory, then loads into LadybugDB under `.gitnexus/`. Repo registered in `~/.gitnexus/registry.json` for MCP discovery." Three query interfaces: MCP (stdio), HTTP bridge (`serve`), and CLI direct (`gitnexus query|context|impact|cypher`). Staleness: "`core/git-staleness.ts` compares indexed `lastCommit` to `HEAD` and classifies the result as `current`, `behind`, `diverged` ... or `unknown`" — [ARCHITECTURE.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/ARCHITECTURE.md)
- 19 MCP tools (17 per-repo + 2 group), verbatim from README table: `list_repos`, `query` ("Process-grouped hybrid search (BM25 + semantic + RRF)"), `context` ("360-degree symbol view — categorized refs, process participation"), `impact` ("Blast radius analysis with depth grouping and confidence"), `trace` ("Shortest directed path between two symbols"), `detect_changes` ("Git-diff impact — maps changed lines to affected processes"), `check`, `rename`, `cypher` ("Raw Cypher graph queries"), `route_map`, `tool_map`, `shape_check`, `api_impact`, `explain` and `pdg_query` (need `--pdg` index), `read_file`, `grep`, `group_list`, `group_sync` — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- MCP resources include `gitnexus://repo/{name}/context` ("Codebase stats, staleness check, and available tools"), `/clusters`, `/processes`, `/schema`; 2 MCP prompts `detect_impact` and `generate_map` — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Community detection: "run `gitnexus analyze --skills` and GitNexus detects the functional areas of your codebase (via Leiden community detection) and generates each one as a direct project skill under `.claude/skills/gitnexus-area-<name>/`" — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md); a vendored `leiden` implementation sits in `gitnexus/vendor/leiden` — [vendor dir](https://github.com/abhigyanpatwari/GitNexus/tree/main/gitnexus/vendor)
- Control-flow/PDG layer is language-limited: "**Control flow (CFG, opt-in `--pdg`)** — per-function control-flow graphs ... currently **TypeScript & JavaScript** (#2081 M1); other languages planned. Off by default." — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Monorepo layout: `gitnexus/` (npm package: CLI, MCP stdio server, HTTP API, ingestion, LadybugDB, embeddings), `gitnexus-web/`, `gitnexus-shared/`, `gitnexus-claude-plugin/`, `gitnexus-cursor-integration/`, `gitnexus-factory-plugin/`, `eval/` — [ARCHITECTURE.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/ARCHITECTURE.md)
- npm package runtime deps (latest 1.6.12) include `tree-sitter@0.21.1`, `@ladybugdb/core@0.18.3`, `graphology`, `@modelcontextprotocol/sdk`, and npm-published grammars for go/cpp/php/java/ruby/rust/python/c-sharp/javascript/typescript; optional deps `onnxruntime-node` and `@huggingface/transformers` (local embeddings) — [npm registry JSON](https://registry.npmjs.org/gitnexus)
- A third-party blog disputes the "zero-server" framing: the web app is a frontend and analysis runs on a local server started with `npx gitnexus@latest serve` on port 4747; without it the UI shows only onboarding (search snippet; page not fetched) — [reskilll blog](https://blogs.reskilll.com/?p=84)

### Inferences
- "Zero-server" is accurate only for the WASM browser UI; for Claude Code use you run a local Node MCP process and a `.gitnexus/` index directory per repo, so operationally it behaves like any other local MCP server.
- The value proposition is explicitly "precomputed structure returned in one tool response" versus the agent chaining greps; the correct comparison baseline for an iOS team is therefore Claude Code's own Grep/Glob/Read plus the `swift-lsp` plugin, not "no tooling."

### Gaps
- No benchmark numbers appear in the README itself; the only token-efficiency wording is qualitative ("no 10-query chains").

## Key Question 2: Does GitNexus support Swift and Objective-C? What happens on an Xcode project?

### Takeaway
Yes, as of Oct 2026 both are supported: Swift via a vendored (optional) `tree-sitter-swift` grammar with SPM and Xcode-target module modeling, and Objective-C via a vendored `tree-sitter-objc` grammar with a documented "MVP" provider for `.m`/`.mm`/content-classified `.h`. Important caveats: Swift is an *optional* grammar that can silently be absent (prebuild mismatch or `GITNEXUS_SKIP_OPTIONAL_GRAMMARS=1`), in which case `.swift` files are simply not parsed; Swift lacks the "Imports"/"Named Bindings" checkmarks in the README table; ObjC has no framework detection, entry-point scoring, or constructor inference; and Swift receiver-resolution bugs are still being filed and fixed weekly.

### Inferences
- On an Xcode project with the Swift grammar loaded, GitNexus will parse `.swift`, `.m`, `.mm` (and ObjC-classified `.h`), group Swift files into modules by `.pbxproj` target or `Package.swift`, and score `@main` App structs and `UIViewController` subclasses as entry points. Storyboards/XIBs, Info.plist, asset catalogs, and `.xcconfig` are not source languages and will not be graph nodes (no evidence of handling found in the clone).
- Because Swift lacks "Imports"/"Named Bindings" in the feature table and cross-module visibility relies on target/package modeling rather than compiler data, cross-module impact results are heuristic. The open issue #3426 (extension calls resolving to unrelated same-name members) shows the practical failure mode: false caller/callee edges in `impact`/`context` for common Swift names (`configure()`, `update()`, `start()`).
- Since the Swift grammar is optional and can "silently soft-fail when no prebuild matches," a team on an unusual Node/arch combination may get an index with zero Swift symbols; the stderr warning is the only signal. This is the single most important pre-flight check (see Part B).
- The ObjC provider is explicitly conservative: dynamic sends are stored as unresolved, so `impact` on ObjC code will under-report runtime-dispatched callers by design.
- tvOS specifics (`#if os(tvOS)`, focus engine APIs) are handled only at the level of generic conditional-compilation preprocessing; there is no tvOS-specific framework detection in `framework-detection.ts`.

### Gaps
- No documentation of per-language index statistics (`gitnexus status`/the `context` resource report only `files`, `symbols`, `processes` — see [mcp/resources.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/mcp/resources.ts)). Verifying Swift coverage therefore requires querying known Swift symbols or a Cypher count (Part B).
- No issues explicitly titled with "Objective-C", "Xcode", "iOS" or "SwiftUI" were visible in the first page of the 255-result GitHub search; bodies were not inspected — [issues search](https://github.com/abhigyanpatwari/GitNexus/issues?q=objective-c+OR+xcode+OR+ios+OR+swiftui)
- No published accuracy numbers for Swift resolution (the `bench/` baselines are internal regression baselines, not accuracy-vs-compiler studies).

## Key Question 3: How does GitNexus plug into Claude Code, and what are its token-cost characteristics?

### Takeaway
`npx gitnexus analyze` indexes and writes skills to `.claude/skills/`, a marked block into `CLAUDE.md`/`AGENTS.md`, and registers PreToolUse (Grep|Glob|Bash) and PostToolUse (Bash) hooks; `npx gitnexus setup` (or `claude mcp add gitnexus -- npx -y gitnexus@latest mcp`) registers the MCP server. Token cost comes from four channels: MCP tool definitions (deferred by default in Claude Code), ~108 KB of SKILL.md across 11 skills (loaded on demand), the CLAUDE.md block (always loaded), and hook-injected `additionalContext` on every Grep/Glob/Bash call. No published measurement of this overhead exists.

### Cited Findings
- Quick start: "`npx gitnexus analyze` ... `npx gitnexus setup` ... `analyze` indexes the codebase, installs agent skills, registers Claude Code hooks, and creates `AGENTS.md` / `CLAUDE.md` context files — all in one command. `setup` writes the MCP config so your AI agent can use the graph." Global install recommended "for faster MCP startup". Manual Claude Code MCP: `claude mcp add gitnexus -- npx -y gitnexus@latest mcp` (Windows: `cmd /c npx ...`) — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Editor support table: "**Claude Code** | Yes | Yes | Yes (PreToolUse + PostToolUse) | **Full**" and "**Claude Code** and **Codex** go deepest: their PreToolUse hooks enrich the search before it runs, and their PostToolUse hooks also detect a stale index after commits and prompt the agent to reindex." — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Hook configuration (verbatim): PreToolUse `"matcher": "Grep|Glob|Bash"` running `node "${CLAUDE_PLUGIN_ROOT}/hooks/gitnexus-hook.js"` with `"timeout": 10` and status message "Enriching with GitNexus graph context..."; PostToolUse `"matcher": "Bash"`, "Checking GitNexus index freshness..." — [gitnexus-claude-plugin/hooks/hooks.json](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus-claude-plugin/hooks/hooks.json)
- The hook injects via `hookSpecificOutput: { hookEventName, additionalContext: message }`; stale message: "GitNexus index is stale (last indexed: <sha7>)" — [gitnexus-claude-plugin/hooks/gitnexus-hook.js](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus-claude-plugin/hooks/gitnexus-hook.js)
- Skills installed: `gitnexus`, `gitnexus-cli`, `gitnexus-debugging`, `gitnexus-exploring`, `gitnexus-guide`, `gitnexus-impact-analysis`, `gitnexus-lfg`, `gitnexus-plan`, `gitnexus-pr-swarm-review`, `gitnexus-refactoring`, `gitnexus-review`, `gitnexus-work`; SKILL.md sizes in the repo: plan 24,158 B, work 16,709 B, review 15,719 B, guide 13,864 B, cli 8,280 B, impact-analysis 7,241 B, refactoring 6,542 B, debugging 5,425 B, lfg 4,517 B, exploring 4,327 B, pr-swarm-review 1,615 B (108,397 B total) — [.claude/skills](https://github.com/abhigyanpatwari/GitNexus/tree/main/.claude/skills)

Opt-outs: `--skip-agents-md`, `--skip-skills`, `.gitnexusrc` `skipContextFiles`/`skipSkills`/`indexOnly` — [gitnexus/src/cli/ai-context.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/cli/ai-context.ts), [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Read-only/allowlist modes: "Environment variables can restrict MCP to read-only tools or an allowlist of repositories"; the `rename` tool mutates files — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Known install issues documented in README: npm 11.x crash (pnpm workaround `pnpm --allow-build=@ladybugdb/core --allow-build=gitnexus --allow-build=tree-sitter dlx gitnexus@latest analyze`), slow cold install, optional grammars need `python3`/`make`/`g++` if no prebuild matches — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)
- Claude Code context accounting: "MCP tool definitions are deferred by default and loaded on demand via tool search, so only tool names and server instructions consume context until Claude uses a specific tool." and "Skills load on demand. Claude sees skill descriptions at session start, but the full content only loads when a skill is used." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Claude Code `/usage` attribution: "recent usage attributed to skills, subagents, plugins, and individual MCP servers, each shown as a percentage of the total. An MCP server's share counts only the requests that consumed one of its tool results." and "Prefer CLI tools when available: Tools like `gh`, `aws`... are still more context-efficient than MCP servers because they don't add any per-tool listing." — [Manage costs](https://code.claude.com/docs/en/costs)
- Mintlify-hosted docs describe `claude mcp add gitnexus -- npx -y gitnexus mcp` and "six agent skill files" (older count than the 11–12 now in the repo) — [Mintlify GitNexus Claude Code page](https://www.mintlify.com/abhigyanpatwari/GitNexus/mcp/claude-code)

### Inferences
- The always-on overhead is the CLAUDE.md block (designed to stay under ~120 lines) plus skill descriptions and MCP tool names; the variable overhead is hook `additionalContext` appended to every Grep/Glob/Bash call, which is the channel most likely to bloat context in a long iOS debugging session (every `xcodebuild`/`grep` invocation is a Bash call that triggers the hook). This is measurable with Claude Code's OTel `tool_result_size_bytes` and `/usage` MCP attribution (Part B).
- A 10-second hook timeout on every Grep/Glob/Bash call adds worst-case latency that should be measured, not assumed.

### Gaps

## Key Question 6: How does GitNexus compare with alternatives that support Swift (Serena, sourcekit-lsp/Claude Code swift-lsp plugin, IndexStoreDB-based tools, Sourcegraph, Aider repo map, etc.)?

### Takeaway
For Swift, the compiler-backed options (Claude Code's official `swift-lsp` plugin, Serena, SwiftLens, IndexStoreDB-based MCPs) give exact definitions/references but need a working build (SwiftPM or `buildServer.json` for `.xcodeproj`) and are macOS/Xcode-bound; GitNexus is build-free and cross-platform but heuristic. The lowest-cost first step for an iOS team is the official `swift-lsp` plugin, which Anthropic maintains and which adds post-edit diagnostics; GitNexus's distinct value is graph-level `impact`/`trace`/`detect_changes` and Objective-C coverage, which none of the LSP routes provide out of the box.

## Key Question 7 (Part B): How should an iOS/tvOS team rigorously evaluate whether GitNexus (or any code-intelligence tool) helps Claude Code? Tasks, metrics, controls, red flags, measurement

### Takeaway
Run a 1–2 week paired A/B on your own repo with pinned versions, fresh worktrees per run, hidden acceptance tests, and headless Claude Code sessions whose `--output-format json`/`stream-json` result and OpenTelemetry events provide the token, cost, duration, and tool-call numbers; precede it with a mandatory "did it actually parse Swift" gate, and treat token savings on failed tasks as failures. The design below is a proposal; it borrows its controls from GitNexus's own `workflow_bench` and from the GitLab GKG study's caveats.

### Cited Findings (measurement mechanics and design precedents)
- Headless runs and cost fields: "With `--output-format json`, the response payload includes `total_cost_usd` and a per-model cost breakdown ... Both figures are client-side estimates"; `session_id` is in the JSON (`jq -r '.session_id'`); `stream-json`'s "last line of the stream is a `result` message with the final response text, cost, and session metadata"; `--bare` "skipping auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory, and CLAUDE.md" and in bare mode you pass `--mcp-config`, `--plugin-dir`, `--settings`; `system/init` event lists `mcp_servers` with `status` and `plugins`/`plugin_errors` so "a CI gate can fail on a non-empty array" — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- `/usage` session block shows "Total cost", "Total duration (API)", "Total duration (wall)", "Total code changes", per-model input/output/cache tokens, and a "Prompt cache (main)" line; plan usage breakdown attributes usage to "individual MCP servers"; `--max-budget-usd` exists; `/context` shows what consumes space (the brief's `/cost` is now documented as `/usage`) — [Manage costs](https://code.claude.com/docs/en/costs)
- OpenTelemetry: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=otlp`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_ENDPOINT`; metrics `claude_code.token.usage` (attrs `type` = input/output/cacheRead/cacheCreation, `model`), `claude_code.cost.usage` (attrs include `mcp_server.name`, `mcp_tool.name`, `skill.name`, `plugin.name`), `claude_code.lines_of_code.count`, `claude_code.active_time.total`; events `claude_code.api_request` (`cost_usd`, `duration_ms`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`), `claude_code.tool_result` (`tool_name`, `tool_use_id`, `success`, `duration_ms`, `tool_input_size_bytes`, `tool_result_size_bytes`; `tool_input` with `OTEL_LOG_TOOL_DETAILS=1`), `claude_code.tool_decision`; "To trace everything triggered by one prompt, filter events by `prompt.id`" — [Monitoring usage](https://code.claude.com/docs/en/monitoring-usage)
- Design precedent (GitNexus's own harness): fresh detached worktree per run, hidden "harness-owned" oracle required for `resolved`, baseline arm with `--disallowedTools Skill`, a `baseline_nomcp` arm to separate skill effects from tool effects, "Token savings on a failed task are flagged, not celebrated," diff churn recorded as an over-engineering proxy, task `class` labels (trivial → investigation → cross-module), report with medians per task per arm — [eval/workflow_bench/README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/eval/workflow_bench/README.md)
- Design precedent (GitLab GKG): 11 runs per configuration because "Anthropic's API has no per-call seed"; the agent "rarely re-indexed ... possibly due to stale data concerns"; token increase attributed to "MCP defaults return about 50 items per call" — [GitLab GKG issue #224](https://gitlab.com/gitlab-org/rust/knowledge-graph/-/issues/224)
- GitNexus verification surfaces: stderr warning "optional grammar \"tree-sitter-swift\" is unavailable — .swift files will not be parsed" — [optional-grammars.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/cli/optional-grammars.ts); `gitnexus://repo/{name}/context` resource prints `stats: files / symbols / processes` and a staleness check — [mcp/resources.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/mcp/resources.ts); CLI equivalents `gitnexus query|context|impact|cypher`, `gitnexus status [--json]`, `gitnexus analyze --branch`, `GITNEXUS_MAX_FILE_SIZE` (512 KB default skip threshold) — [README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md), [ARCHITECTURE.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/ARCHITECTURE.md); ObjC acceptance bar from the provider doc: "`query \"SYModuleCaller\"` yields class/method semantic nodes, not only file nodes" — [objective-c-provider.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/docs/languages/objective-c-provider.md)
- Claude Code LSP plugin verification: a diagnostics line "Found N new diagnostic issues in M files" after an edit means the server started; `/plugin` → Errors tab shows `Executable not found in $PATH` — [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence)

### Proposed methodology (inference/synthesis; cite the items above when adopting)

**0. Pre-flight gate: prove the tool parsed Swift/ObjC (run before any A/B; fail → stop).**
1. Pin versions: `npm i -g gitnexus@1.6.12` (not `@latest`; RCs ship several times a day per the npm registry). Record Node version, macOS/arch, Claude Code version (`claude --version`), model id, and the git SHA of the index.
2. Run `gitnexus analyze` from the repo root and capture stderr; any line containing `optional grammar "tree-sitter-swift" is unavailable` or `disabled via GITNEXUS_SKIP_OPTIONAL_GRAMMARS` is a hard fail.
3. Read `gitnexus://repo/<name>/context` (or `gitnexus status --json`): record `files`, `symbols`, `processes`. Compare `files` to `git ls-files | grep -E '\.(swift|m|mm|h)$' | wc -l`; a large shortfall means unparsed files (also check `GITNEXUS_MAX_FILE_SIZE` skips for big generated Swift files).
4. Symbol spot-checks (10 Swift, 5 ObjC): pick known symbols (your `@main` App struct, a `UIViewController` subclass, a SwiftUI `View`, a protocol with extension default, an ObjC category method with a multi-part selector). Run `gitnexus context <Symbol>` and `gitnexus impact <method>`; require (a) a class/method node, not just a file node, (b) the file path and line are right, (c) callers match a hand-verified `grep -rn`/Xcode "Find Call Hierarchy" list. Score precision/recall of callers per symbol; set an acceptance threshold (e.g., ≥0.8 precision on direct callers) before proceeding.
5. Cypher count check: `gitnexus cypher "MATCH (n) WHERE n.filePath ENDS WITH '.swift' RETURN count(n)"` (schema via `gitnexus://repo/<name>/schema`); zero or near-zero Swift nodes = fail.
6. Xcode module check: for an `.xcodeproj` without `Package.swift`, confirm that app-target and extension-target files resolve to separate modules (the `swift-xcode-targets` fixture pattern): a method defined in both App and Widget targets must not cross-link.
7. tvOS check: a symbol declared inside `#if os(tvOS)` must appear in `context`; a focus-related override (e.g., `didUpdateFocus(in:with:)`) must be found by `query`.
8. Staleness check: make a commit, run a Bash tool call in Claude Code, and confirm the PostToolUse hook emits the "GitNexus index is stale" message; then measure how long `gitnexus analyze` incremental re-index takes on your repo (budget it per task).

**1. Arms (paired on the same task, same base commit, same model, same CLAUDE.md, same permission mode).**
- A0 `baseline_nomcp`: Claude Code with built-in Grep/Glob/Read/Bash only (`--bare -p` plus `--settings` with your real CLAUDE.md appended via `--append-system-prompt-file` so content is identical across arms; `--disallowedTools Skill` if skills exist).
- A1 `lsp`: A0 + `swift-lsp` plugin (`--plugin-dir`), with `buildServer.json` generated by `xcode-build-server` after a fresh Xcode build (verify the diagnostics line appears once).
- A2 `gitnexus_tools`: A0 + GitNexus MCP only (`--mcp-config`), skills and hooks disabled (`gitnexus analyze --skip-skills --skip-agents-md` or `.gitnexusrc` `indexOnly`).
- A3 `gitnexus_full`: A2 + GitNexus skills + CLAUDE.md block + PreToolUse/PostToolUse hooks (the vendor's "Full" configuration).
- A4 (optional) `lsp+gitnexus_full`: tests the GKG finding that stacking can hurt.
Run each (task × arm) ≥5 times (GitLab used 11; the API has no seed). Use a fresh `git worktree` per run; delete `.gitnexus/` and re-analyze per worktree so index staleness is controlled.

**2. Representative tasks (8–12, labelled trivial / investigation / cross-module / UI+network; mix Swift-only, ObjC-only, mixed).**
- Crash triage: give a symbolicated crash log (e.g., `EXC_BAD_ACCESS` in a Combine sink, or a main-thread checker violation) and ask for root cause + fix; hidden oracle = a unit test reproducing the crash now passes.
- Cross-module refactor: rename/retype a model property used across app target, widget extension, and test bundle; oracle = `xcodebuild build-for-testing` succeeds for all targets and hidden tests pass (counts files touched vs. ground-truth set → recall/precision of impact).
- Feature add touching UI + networking: new SwiftUI screen backed by a new endpoint in the networking layer with an injected client; oracle = hidden tests for view model + URLProtocol-stubbed request.
- tvOS focus bug: a `UICollectionView`/SwiftUI focus regression (e.g., `focusable`/`prefersDefaultFocus`, `didUpdateFocus(in:with:)` not invalidated); oracle = XCTest on tvOS simulator with hidden focus assertions.
- ObjC bridging: fix a nullability/selector mismatch between an ObjC category and Swift caller; oracle = hidden test + build.
- Pure navigation question ("list all call sites of X across targets"): oracle = exact set; measures retrieval precision/recall directly.
- Dead-code/impact question ("what breaks if I delete Y?"): oracle = compile result after deletion.

**3. Metrics per run (from the `stream-json` final `result` event and OTel).**
- Correctness: `resolved` (hidden oracle passes), `builds` (first `xcodebuild` success), review defects found by a human reviewer blind to arm, hallucinated-API count (any symbol/API referenced that does not exist in the SDK or repo; count via compiler errors + reviewer check).
- Efficiency: `total_cost_usd`, input/output/cacheRead/cacheCreation tokens by model (`claude_code.token.usage`), `num_turns`, wall-clock and API duration, tool-call count and per-tool distribution (`claude_code.tool_result.tool_name`), MCP share of cost (`claude_code.cost.usage{mcp_server.name="gitnexus"}`), bytes injected by hooks (`tool_result_size_bytes` and `tool_input_size_bytes` deltas between A2 and A3), time-to-first-correct-build.
- Process: number of GitNexus tool invocations per run and whether `impact`/`context` results were actually used (GitLab found the model often bypassed the graph); re-index count; diff churn (files/+/−) vs. ground truth.
- Report medians and interquartile ranges per task per arm; flag any arm that "saves tokens" on tasks it fails.

**4. Controls and hygiene.**
- Identical model id, effort/thinking settings, permission mode (`--permission-mode acceptEdits` + explicit `--allowedTools` incl. `Bash(xcodebuild *)`), identical CLAUDE.md text, no auto-memory (`--bare`), same Xcode/toolchain, simulators pre-booted, network stubbed.
- Hidden tests live outside the worktree the agent sees; the agent only gets the task prompt.
- Randomize run order; run arms interleaved to spread API variance; cap each run with `--max-turns` and `--max-budget-usd`.
- Pre-register the acceptance thresholds (e.g., "adopt if resolve rate improves ≥10 points on cross-module tasks with no cost increase >20%, or cost drops ≥25% with no resolve-rate loss").

**5. Red flags that should stop or discount the evaluation.**
- Swift grammar warning at analyze time, or Swift node count ≈ 0 (tool is indexing only non-Swift files such as build scripts/JSON/JS in RN/hybrid apps).
- `impact`/`context` returning unrelated same-name members (the open issue #3426 pattern); measure false-caller rate on overloaded names like `configure`, `start`, `update`.
- Stale index: PostToolUse stale warnings appearing mid-task and the agent re-analyzing (count re-index events and their wall time).
- Hook latency: Grep/Glob/Bash calls slowed by the 10 s hook timeout; compare `tool_result.duration_ms` for `Grep` between A0 and A3.
- Context bloat: hook `additionalContext` or skill loads pushing sessions into compaction (watch `/usage` cache-miss and "expected rebuild" counts, and `claude_code.token.usage{type="cacheCreation"}` spikes).
- MCP overhead without use: GitNexus tools listed but called 0–1 times per run while cost rises.
- Non-reproducibility: resolve rate varying by >2 tasks across repeats (as in GKG's 5–7/23 spread) — increase repetitions before concluding.
- License: using GitNexus in a commercial product/workflow without an Akon Labs license.

**6. For non-GitNexus tools, the same gate applies**: for LSP-based tools, confirm `buildServer.json` points at a current DerivedData build root and that `findReferences` on a cross-target symbol returns hits from all targets; for IndexStoreDB tools, confirm the index store was built with `-index-store-path` after the latest commit.

### Gaps
- No published iOS/Swift benchmark exists to borrow tasks from; the task set above must be built by the team.
- Claude Code's hidden-oracle and worktree isolation are team-implemented; GitNexus's `workflow_bench` runner is a reference but is tied to its own skills and Bubblewrap Linux containment (not macOS/Xcode).
