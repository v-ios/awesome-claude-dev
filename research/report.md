# Closed verification loops make Claude Code ship iOS

Top-tier mobile engineers do not get their results from Claude Code through clever prompts; they get them by turning the tool into a closed, verifiable loop: a check the agent can run on its own (an `xcodebuild` exit code, a targeted `-only-testing:` run, a simulator screenshot), a plan reviewed before any code is written, one task per named session or git worktree, and a context window kept deliberately small. That pattern is stated almost verbatim in Anthropic's official best-practices page, in Claude Code lead Boris Cherny's public tips, and in every substantive first-hand Apple-platform account we found (Karunaratne, Trott, Wals, Bartlett, Duolingo, Shopify). On Apple platforms the loop is harder to close than on the web because `xcodebuild` is slow and emits thousands of lines, `.pbxproj` files are hostile to text edits, and until Xcode 26.3 (February 2026) no first-party path existed for an external agent to drive Xcode or the simulator. The tooling has now caught up: headless `xcodebuild` plus `xcresulttool`, the `xcbeautify`/`xcsift` output filters, Sentry's MobileBuildMCP (the renamed XcodeBuildMCP), Apple's own Xcode MCP server reached through `xcrun mcpbridge`, and Xcode 27's headless `mcp-server` preview with tvOS Siri Remote tools. Claude Code's governance surface (`CLAUDE.md`, `.claude/rules/`, hooks, permissions, the OS sandbox, managed settings) is mature enough to *enforce* architecture rather than merely describe it, and the strongest real-world Swift template enforces every boundary twice. For tvOS specifically, no named practitioner has published a Claude Code account, but Apple's focus-debugging APIs (`UIFocusDebugger`, `-UIFocusLoggingEnabled`), `XCUIRemote`, Device Hub's keyboard mapping and idb's new `ui remote` command compose into a workable agent loop. GitNexus, the code-graph tool a colleague recommended, does parse Swift and Objective-C as of October 2026 (the brief's assumption that it did not is wrong), but it is PolyForm-Noncommercial licensed, heuristic rather than compiler-backed, publishes no Swift accuracy numbers, and the independent evidence for code-graph tools in general is thin and mixed; the only defensible way to decide is a paired A/B on your own repository with a mandatory "did it actually parse Swift" gate, which this report specifies. Ready-to-copy files for everything below live in the repository at `playbook/`.

A second cross-cutting caveat matters for a team reading older blog posts: Claude Code renamed or removed several features during 2026. ## Objective 1: elite workflows plan first, verify always, and isolate every task

Anthropic's own guidance reduces to one constraint and five moves, and the practitioner record confirms them. The constraint: "Claude's context window fills up fast, and performance degrades as it fills ... The context window is the most important resource to manage" **[Official]** ([Best practices](https://code.claude.com/docs/en/best-practices)). The first move is a check Claude can run: "Give Claude a way to verify its work ... It's the difference between a session you watch and one you walk away from," where the check "is anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot," and the agent must "show evidence rather than asserting success" ([Best practices](https://code.claude.com/docs/en/best-practices)). The second is explore → plan → implement → commit, with the explicit caveat "If you could describe the diff in one sentence, skip the plan." The third is specificity: name the files, the example pattern to follow, the constraints and what "fixed" looks like. The fourth is aggressive context hygiene (`/clear` between tasks, `/compact <focus>` at milestones, `/btw` for side questions, subagents for research). The fifth is scaling out with worktrees and headless runs. Boris Cherny's public tips add the lived habits **[Secondhand]**: "The single biggest productivity unlock" is 3–5 git worktrees with one Claude in each, run in numbered terminal tabs with iTerm2 notifications so he never waits on a single process; complex tasks start with "Shift+Tab twice" into plan mode and he re-plans rather than pushing a failing approach; verification "Will 2–3x the quality of the final result"; and "Anytime we see Claude do something incorrectly we add it to the CLAUDE.md," then every six months he deletes CLAUDE.md, skills and hooks and re-adds only what the model still gets wrong ([SKZL-AI playbook TIPS.md](https://raw.githubusercontent.com/SKZL-AI/boris-cherny-claude-code-playbook/main/TIPS.md); [YC library](https://www.ycombinator.com/library/UN-boris-cherny-building-claude-code)). He runs `/effort` at xhigh for most tasks and max for the hardest, and names "Over-specification" as "the #1 experienced-engineer mistake." Thariq Shihipar of the same team adds that `/goal` is worth using "only if you have a verifiable finish line" and that the team cut its system prompt by about 80% when models changed, so instruction files should be re-audited after every model upgrade ([creatoreconomy.so](https://creatoreconomy.so/p/how-i-plan-build-and-run-loops-with-claude-code-thariq-shihipar)).

### The session-management commands that matter, in the order a day uses them

The documented CLI surface is large, but the launch lines an iOS engineer actually needs are few **[Official]** ([CLI reference](https://code.claude.com/docs/en/cli-reference); [Manage sessions](https://code.claude.com/docs/en/sessions); [Worktrees](https://code.claude.com/docs/en/worktrees)):

```bash
# Explore/plan a task without touching source (reads + classifier-approved commands)
claude --permission-mode plan

# One isolated worktree per task, in its own tmux session; branch is worktree-<name>
claude -w fix-crash-1234 --tmux          # add .claude/worktrees/ to .gitignore
# Copy gitignored local files (xcconfig secrets, .xcode.env) into each worktree
printf 'Config/Local.xcconfig\n.xcode.env\n' > .worktreeinclude

# Name sessions like branches; resume by name, by PR, or from the picker
claude -n player-scrub-bug               # or /rename inside the session
claude --resume player-scrub-bug "finish the PR"
claude --from-pr 1234                    # sessions auto-link to PRs Claude created
claude --continue --fork-session         # branch a conversation instead of interleaving it

# Inside a session
/compact Focus on the files changed, the xcodebuild/test commands used, and open TODOs
/clear release-prep                      # names the conversation you are leaving
/btw does Combine's sink retain self here?   # never enters the transcript
/goal xcodebuild test -only-testing:AppTests passes and git status is clean, or stop after 20 turns
/loop 5m check whether CI passed and address any review comments
```

Several details in those pages change iOS practice. Checkpoints (`Esc Esc`, `/rewind`) "only track changes made through Claude's file editing tools. Changes made through Bash commands or external processes are not captured. This isn't a replacement for git" ([Best practices](https://code.claude.com/docs/en/best-practices)); because `xcodegen generate`, `pod install` and `swift package resolve` are all Bash-driven, an iOS team should commit at milestones rather than rely on rewind for project regeneration **[Inference]**. Resuming restores history, model, permission mode, an active `/goal` and unexpired scheduled tasks, but *not* `--mcp-config`, `--settings`, `--plugin-dir`, `--fallback-model` or `--add-dir`, which must be passed again ([Manage sessions](https://code.claude.com/docs/en/sessions)). Worktrees are fresh checkouts, so DerivedData is not shared and every parallel session pays a cold Xcode build; the `worktree.baseRef: "head"` setting and `.worktreeinclude` reduce setup, but a team should expect to run parallel sessions on separate schemes or packages rather than five full-app rebuilds **[Inference]**. The `/goal` evaluator "doesn't run commands or read files independently" and judges only what Claude surfaces, so the prompt should instruct Claude to print the final `BUILD SUCCEEDED`/`TEST FAILED` lines; "Background work defers evaluation," so a long build running in the background delays the check ([Goal](https://code.claude.com/docs/en/goal)). The official course-correction rule is blunt: "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt" ([Best practices](https://code.claude.com/docs/en/best-practices)).

Headless mode is the second half of the daily toolkit. `claude -p "<prompt>" --output-format json | jq -r '.result'` returns a result with session ID and cost; `--bare` skips "auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory, and CLAUDE.md," is "the recommended mode for scripted and SDK calls," and requires `ANTHROPIC_API_KEY`; `--allowedTools "Bash(git diff *),Bash(git log *)"` uses the permission syntax where "The trailing ` *` enables prefix matching ... without it, `Bash(git diff*)` would also match `git diff-index`"; unattended runs use `--permission-mode dontAsk` or, from v2.1.259, `--permission-prompts none` ([Run Claude Code programmatically](https://code.claude.com/docs/en/headless)). The canonical fan-out is a shell loop, "Test on a few files, then run on all of them": `for file in $(cat files.txt); do claude -p "Migrate $file ... Return OK or FAIL." --allowedTools "Edit,Bash(git commit *)" --permission-mode dontAsk; done` ([Best practices](https://code.claude.com/docs/en/best-practices)). For iOS triage the piped form is the useful one: `cat build-error.txt | claude -p 'concisely explain the root cause of this build error'` ([Headless](https://code.claude.com/docs/en/headless)).

### Prompt structures for features, bugs and refactors, with the iOS adaptation

The official before/after pairs are the template **[Official]**. For a feature: not "add a calendar widget" but "look at how existing widgets are implemented on the home page to understand the patterns. HotDogWidget.php is a good example. follow the pattern to implement a new calendar widget ... build from scratch without libraries other than the ones already used in the codebase." For a bug: not "fix the login bug" but "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it." For a build failure: "the build fails with this error: [paste error]. fix it and verify the build succeeds. address the root cause, don't suppress the error" ([Best practices](https://code.claude.com/docs/en/best-practices)). The common-workflows page already uses a Swift example for test generation: "find functions in NotificationsService.swift that are not covered by tests" → "add tests for the notification service" → "add test cases for edge conditions" → "run the new tests and fix any failures," and for refactors it advises "Do refactoring in small, testable increments" ([Common workflows](https://code.claude.com/docs/en/common-workflows)). Two larger structures complete the set: the interview-to-spec prompt ("Interview me in detail using the AskUserQuestion tool ... Keep interviewing until we've covered everything, then write a complete spec to SPEC.md," then "start a fresh session to execute it") and the adversarial review ("Use a subagent to review the rate limiter diff against PLAN.md. Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences") ([Best practices](https://code.claude.com/docs/en/best-practices)). Peter Steinberger's "give me options" prompt is the practitioner addition: when he disliked a fix he asked for options and "learned an approach I totally didn't think of" **[Snippet]** ([x.com/steipete](https://x.com/steipete/status/1937184376657265077)).

No official page gives an iOS crash-report prompt, so the following combines the documented structure with Apple artifacts **[Inference]**. It points at a file, names the reproduction command, demands a failing test first, forbids suppression, and asks for evidence:

```text
Crash: EXC_BAD_ACCESS, symbolicated crashed-thread frames pasted below (from the .ips).
Repro: xcodebuild test -scheme App -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:AppTests/PlayerTests/testScrubAfterSeek -quiet
Start in Features/Player/PlayerViewModel.swift, especially the Combine sink in startObserving().
Write a failing Swift Testing test that reproduces the crash first, then fix the root cause.
Do not suppress the error, add try?, or weaken the test. Re-run that single test and the iOS
and tvOS builds, and paste the last 20 lines of each as evidence.
```

Because `@file` includes up to 25,000 tokens of a file, pointing at a Swift file is cheap, but `@`-including an `.xcresult` or a raw `xcodebuild` log is not; logs should be filtered first (see Objective 2) ([Best practices](https://code.claude.com/docs/en/best-practices)).

### What the practitioner record and the numbers actually support

The consensus among the first-hand Apple accounts formed in mid-2025 and has held: Claude Code is "okay at Swift and good at SwiftUI," struggles with Swift Concurrency (5.5+), "often falls back on outdated Objective-C APIs," and becomes reliable only when it "is capable of independently driving feedback loops" (Indragie Karunaratne, ~20,000 lines of a shipped macOS app with fewer than 1,000 written by hand) **[Snippet]** ([indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code); [Simon Willison](https://simonwillison.net/2025/Jul/6/macos-app-built-entirely-by-claude-code/); [heise.de](https://www.heise.de/en/news/When-AI-programs-a-Mac-app-Developer-reports-on-experiences-10480791.html)). Chris Trott found Claude "knew how to call xcodebuild without setup, but was very inconsistent on which build flags, simulators, OS versions, etc. it picked," and spent a month in December 2025 "closing the loop" through build, install/launch, console, simulator control and device stages **[Snippet]** ([twocentstudios, Jun 2025](https://twocentstudios.com/2025/06/22/vinylogue-swift-rewrite/); [twocentstudios, Dec 2025](https://twocentstudios.com/2025/12/27/closing-the-loop-on-ios-with-claude-code/)). Donny Wals hands a crash report to an agent and returns to a reviewable PR, keeps an `agents.md` rulebook "that grows whenever an agent does something he doesn't want," and argues plan review is where bad architecture gets caught **[Snippet]** ([donnywals.com](https://www.donnywals.com/setting-up-a-delivery-pipeline-for-your-agentic-ios-projects/)). Jacob Bartlett, running several parallel agents daily for over a year, calls "automatic verification ... the backbone of agent parallelism": without self-checking a screen takes 5–10 minutes of supervision, with it sessions "stretch to an hour or overnight" **[Snippet]** ([Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/advanced-agentic-engineering)). The two detailed company write-ups converge on the same control structure. Duolingo's iOS unit-test pipeline produced **250 accepted PRs and ~85,000 lines of test code in ~17 weeks**, after early batches merged at only 47–48% and the team rewrote its rules to stop "mock type mismatch, Swift 6 Sendable, SwiftTesting/XCTest mixing" ([blog.duolingo.com](https://blog.duolingo.com/ai-ios-unit-test-generation-pipeline/)). Shopify's Helix workflow rebuilt the Shop app natively in **12 weeks** by having an agent propose "small, ordered slices of work" where "Each checkpoint must prove its behavior with tests, match the reference ... app in a visual review, pass two adversarial code reviews, and get an engineer's approval," while admitting "Agentic control of simulators has been a bottleneck" ([shopify.engineering/helix](https://shopify.engineering/helix); [shopify.engineering/shop-app-migration](https://shopify.engineering/shop-app-migration)). Two reversals deserve weight: Steinberger, one of the loudest 2025 advocates, wrote by October 2025 that he had moved to Codex, that Claude "gets unreliable well before it fills its window," and that "models will get around a hook if they're determined to" **[Snippet]** ([steipete.me](https://steipete.me/posts/just-talk-to-it)); and Karunaratne doubts "a terminal interface will end up being the ideal UX" ([x.com/indragie](https://x.com/indragie/status/1945293451668369509)).

The productivity numbers are directional, not controlled. Anthropic reports "a 67% increase in PRs merged per engineer per day" and "70–90% of code is now being written with Claude Code assistance," with the caveat that "pull requests alone are an incomplete measure of developer velocity" ([Contribution metrics](https://claude.com/blog/contribution-metrics)); its internal survey of 132 staff found a self-reported boost of "about +50% now, up from about +20% 12 months earlier," debugging as the most common daily use (55%), and "more than half say they can fully delegate only 0–20% of their work," with selection and recall biases listed and METR's finding that experienced developers overestimate AI gains acknowledged ([How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)). The METR randomized trial itself could not be fetched and is listed under unverified items. The one Swift-specific adoption signal is that in May 2026, 33,098 public-GitHub Swift PRs (30.7% of all Swift PRs) carried an agent mark, with Claude Code the largest share, from an index still in preview ([amplifying.ai](https://amplifying.ai/coding-agents/segments/swift)).

## Objective 2: xcodebuild, simctl and two MCP layers close the Apple loop

### The canonical headless build-and-test invocation and how to keep its output small

Every element of the following invocation is documented in the `xcodebuild` man page, Apple's TN2339, the Xcode release notes or the tool READMEs **[Official]/[Source]**; the composition is ours **[Inference]** and must be run once locally because simulator device names change with each Xcode (confirm with `xcrun simctl list devicetypes`).

```bash
set -o pipefail
rm -rf build/App.xcresult                       # -resultBundlePath errors if the path exists
NSUnbufferedIO=YES xcodebuild test \
  -workspace App.xcworkspace -scheme App \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -derivedDataPath ./.derivedData \
  -clonedSourcePackagesDirPath ./.spm \
  -disableAutomaticPackageResolution -skipPackagePluginValidation -skipMacroValidation \
  -resultBundlePath ./build/App.xcresult \
  -only-testing:AppTests/PlayerTests \
  -quiet 2>&1 | xcbeautify -qq --is-ci

# tvOS: same scheme or a tvOS scheme; generic destination for build-only
xcodebuild build -scheme App-tvOS -destination 'generic/platform=tvOS Simulator' -quiet
xcodebuild test  -scheme App-tvOS -destination 'platform=tvOS Simulator,name=Apple TV 4K (3rd generation)' -quiet

# Inner loop: compile once, then re-run single tests without recompiling
xcodebuild build-for-testing -workspace App.xcworkspace -scheme App -destination 'platform=iOS Simulator,name=iPhone 17' -quiet
xcodebuild test-without-building -xctestrun ./.derivedData/Build/Products/App_iphonesimulator*.xctestrun \
  -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:AppTests/PlayerTests/testScrubAfterSeek -quiet
```

The man page defines `-only-testing` identifiers as `TestTarget[/TestClass[/TestMethod]]`, `-quiet` as "Do not print any output except for warnings and errors," `-resultBundlePath` as a bundle containing "build logs, code coverage reports, XML property lists with test results, screenshots and other attachments" which "will exit with an error" if the path exists, and `build-for-testing`/`test-without-building` as the pair that produces and consumes an `.xctestrun` file ([xcodebuild(1)](https://keith.github.io/xcode-man-pages/xcodebuild.1.html)). Apple's own TN2339 supplies the tvOS destination form `platform=tvOS Simulator,id=<UDID>` and the `-workspace` rule ("Use this option when your scheme is contained in an Xcode workspace") ([TN2339](https://developer.apple.com/library/archive/technotes/tn2339/_index.html)). Xcode 16 fixed `xcodebuild` "silently select[ing] the first compatible run destination when it fails to match the destination specifier," and Xcode 26 added `-only-test-configuration <name>` for `test-without-building` and CLI runtime installs via `xcodebuild -downloadPlatform iOS -exportPath …` / `xcrun simctl runtime add <dmg>` ([Xcode 16 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-16-release-notes); [Xcode 26 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes)).

Output volume is the iOS-specific context killer. `xcbeautify` 3.2.1 documents `-q/--quiet` ("Only print tasks that have warnings or errors"), `--quieter`/`-qq` ("Only print tasks that have errors"), `--is-ci` ("Print test result too under quiet/quieter flag"), the `NSUnbufferedIO=YES ... 2>&1 | xcbeautify` form for parallel testing, and GitHub/TeamCity/Azure renderers **[Source]** ([xcbeautify source](https://github.com/cpisciotta/xcbeautify/blob/main/Sources/xcbeautify/Xcbeautify.swift); [README](https://github.com/cpisciotta/xcbeautify)). `xcsift` is the agent-oriented alternative: it "prioritizes information density" over human readability, is used as `xcodebuild build 2>&1 | xcsift` (always `2>&1`), offers a TOON format claimed at "30-60% fewer tokens," installs a Claude Code plugin with `xcsift install-claude-code`, and can proxy Apple's Xcode MCP (`xcsift mcp -- xcrun mcpbridge`) ([xcsift README](https://github.com/ldomaradzki/xcsift)). Practitioners agree on the problem: Trott added `--quiet` because unfiltered output "can quickly overflow the context window, especially when the build fails" **[Snippet]** ([twocentstudios](https://twocentstudios.com/2025/06/22/vinylogue-swift-rewrite/)); FlowDeck's vendor post describes the failure mode as "xcodebuild dumps 2,000 lines into one stream. The agent burns context looking for the error on line 847, misreads a linker error as a warning, retries with the wrong flag" **[Snippet]** ([flowdeck.studio](https://flowdeck.studio/blog/2026/04/11/how-to-set-up-claude-code-for-ios-development/)); Antoine van der Lee's audit of 1,674 agent sessions flags "unfiltered build output as major token costs" **[Snippet]** ([Future of iOS Engineering](https://www.futureofios.com/)). Claude Code itself warns at 10,000 MCP output tokens, truncates at 25,000 by default (`MAX_MCP_OUTPUT_TOKENS` raises it), and spills text results over 50,000 characters to a file ([MCP](https://code.claude.com/docs/en/mcp)).

Result extraction changed with Xcode 16 and the old form now errors. The legacy `xcrun xcresulttool get --format json --path X.xcresult` prints "Error: This command is deprecated and will be removed in a future release, --legacy flag is required to use it" ([Apple Developer Forums 763888](https://developer.apple.com/forums/thread/763888)). The current sequence, from the man page **[Official]** ([xcresulttool(1)](https://keith.github.io/xcode-man-pages/xcresulttool.1.html)):

```bash
xcrun xcresulttool get test-results summary --path build/App.xcresult --compact   # totals + testFailures
xcrun xcresulttool get test-results tests   --path build/App.xcresult --compact   # find testIdentifier
xcrun xcresulttool get test-results test-details --path build/App.xcresult --test-id 'PlayerTests/testScrubAfterSeek()' --compact
xcrun xcresulttool export attachments --path build/App.xcresult --output-path ./out --only-failures
xcrun xcresulttool get log --type console --path build/App.xcresult --compact
xcrun xcresulttool help get test-results summary                                  # prints the JSON schema
```

The summary's top-level fields include `result`, `totalTestCount`, `passedTests`, `failedTests`, `skippedTests` and `testFailures` (Apple DTS, same thread); DTS also noted that `get build-results` may omit warnings the `--legacy` path still shows ([thread 769351](https://developer.apple.com/forums/thread/769351)).

### Swift Package Manager and CocoaPods inside an agent loop

Apple's CI guidance is unambiguous and maps directly onto agent hygiene: "be sure to commit your project's `Package.resolved` file ... If your CI pipeline uses the `xcodebuild` command directly, also pass the `-disableAutomaticPackageResolution` flag. This flag ensures that the CI pipeline always uses the package dependencies as defined in the `Package.resolved` file," and pass `-scmProvider system` to use the Mac's Git and SSH configuration for private packages **[Official]** ([Building Swift packages in CI](https://developer.apple.com/documentation/xcode/building-swift-packages-or-apps-that-use-them-in-continuous-integration-workflows)). `-skipMacroValidation` and `-skipPackagePluginValidation` are not documented on any Apple page; their existence is evidenced by MobileBuildMCP, which always appends `-skipMacroValidation` because it "avoids errors in projects that use Swift Macros," and by Swift Package Index's build logs and forum reports of plugin trust failures that a one-time build in Xcode can clear **[Source]** ([MobileBuildMCP README](https://github.com/getsentry/MobileBuildMCP/blob/main/README.md); [Apple Developer Forums 801663](https://developer.apple.com/forums/thread/801663)). Keeping `-clonedSourcePackagesDirPath` and `-derivedDataPath` under the same parent works when the derived-data folder is dot-prefixed ([Swift Forums 59055](https://forums.swift.org/t/swiftpm-package-build-via-xcodebuild-with-specified-derived-data-path/59055)). For pure packages, `swift test` supports `--filter`, `--skip`, `--parallel`, `--xunit-output`, `--enable-code-coverage` and, in Xcode 27, `--maximum-repetitions` with `--repeat-until [pass|fail]` plus an end-of-run failure summary ([SwiftTest.md](https://github.com/swiftlang/swift-package-manager/blob/main/Sources/PackageManagerDocs/Documentation.docc/SwiftTest.md); [Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)). CocoaPods projects must be built through the `.xcworkspace`; `pod install` exits `31` for "Spec not found (i.e out-of-date source repos, mistyped Pod name etc...)," `--repo-update` forces a specs update, and `--deployment` "Disallow[s] any changes to the Podfile or the Podfile.lock during installation," which is the flag an agent should run with so it can never silently bump a dependency **[Source]** ([CocoaPods install.rb](https://github.com/CocoaPods/CocoaPods/blob/master/lib/cocoapods/command/install.rb)). Project-file churn is the remaining sore point: no elite practitioner described a `.pbxproj` strategy, the only guidance being Tuist's explanation of why group/file references conflict and the community pattern of routing project changes through an XcodeGen `project.yml` ("`MyApp.xcodeproj` is generated — edit `project.yml` instead") ([tuist.dev](https://tuist.dev/blog/2025/03/21/git-conflicts); [ios-template AGENTS.md](https://github.com/tomada1114/ios-template/blob/main/AGENTS.md)).

### Simulators: simctl is the backbone and screenshots plus accessibility dumps are the eyes

Apple publishes no web reference for `xcrun simctl`, so the authoritative evidence is tool source. MobileBuildMCP shells out to exactly these forms **[Source]**: `simctl list devices available --json`, `simctl boot <udid>`, `simctl bootstatus <udid> -b`, `simctl install <udid> App.app`, `simctl launch --terminate-running-process …`, `simctl launch --console-pty` (stdout/`print` only), `simctl terminate <udid> <bundleId>`, `simctl io <udid> screenshot /tmp/shot.png`, `simctl status_bar <udid> clear`, `simctl ui <udid> appearance dark`, and `simctl spawn <udid> log stream --predicate …` for `os.Logger` output, which the server's comments note is captured separately from stdout ([MobileBuildMCP src](https://github.com/getsentry/MobileBuildMCP/tree/main/src); [simulator-launch-oslog-sessions.ts](https://github.com/getsentry/MobileBuildMCP/blob/main/src/utils/log-capture/simulator-launch-oslog-sessions.ts)). Environment variables reach a launched app through the `SIMCTL_CHILD_` prefix "because `simctl launch` does not support `--env/--envs` on all Xcode versions" ([ios-simulator-mcp README](https://github.com/joshuayoes/ios-simulator-mcp)). Xcode 27 added `simctl … reboot` and ships simulator runtimes with "a pre-built dyld cache" for faster first launch ([Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)). The vision loop an agent should run is a screenshot paired with an accessibility dump (`idb ui describe-all` or MobileBuildMCP `snapshot_ui`) so it learns *which element is focused* rather than guessing from pixels **[Inference]**; Karunaratne's 2025 complaint that "There isn't a good equivalent to Playwright yet" is exactly the gap these tools now fill ([Simon Willison](https://simonwillison.net/2025/Jul/6/macos-app-built-entirely-by-claude-code/)).

### Three MCP layers, and which failure mode each one has

As of October 2026 there are three complementary layers, and practitioners run two of them together. The first is **Apple's own Xcode MCP server** (Xcode 26.3+, which "introduces support for agentic coding … powered by coding agents from Anthropic and OpenAI" and "makes its capabilities available through the Model Context Protocol" with "a comprehensive permissions system") **[Official]** ([Xcode 26.3 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_3-release-notes)). Setup is Xcode > Settings > Intelligence > "Allow external agents to use Xcode tools," then:

```bash
claude mcp add --transport stdio xcode -- xcrun mcpbridge
claude mcp list
```

with Apple's warning: "Before prompting an external agent (outside of Xcode), be sure to open your project in Xcode" ([Giving external agents access to Xcode](https://developer.apple.com/documentation/xcode/giving-external-agents-access-to-xcode)). Known 26.3 issues include multiple "Allow Connection?" dialogs, skills "rejected by agents when directly invoked by '/skill'" (say "use the `{skill-name}` skill"), and an irreversible project-access denial for Desktop/Downloads/Documents folders ([Xcode 26.3 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_3-release-notes)). Xcode 27 extends this server with tools "to debug projects by manipulating the active run state, interacting with and reading the contents of the debugger console; listing and switching between available schemes and run destinations and inspecting and modifying build settings, compiler flags, entitlements, and Info.plist keys," lets agents "boot simulators, install and launch apps, synthesize touch events, and capture screenshots," and, crucially for this team, states that "Coding Intelligence agents can now verify tvOS apps, navigating with the Siri Remote to move focus, select, and go Home, and entering text into focused fields." It also ships `lldb-mcp` and a headless preview: "a new MCP server experience that runs without requiring an open Xcode workspace… `sudo xcrun mcp-server enable` … `xcrun mcp-server status`," with `--unsafe-always-allow-all-agents` for unattended environments that is "not a recommended configuration for at-desk use" ([Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)). The failure mode, per Blake Crosley, is that this route "stops working if Xcode crashes or is closed" **[Snippet]** ([blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code)).

The second layer is **MobileBuildMCP**, which v2.7.1 "Renamed … from XcodeBuildMCP" with new npm package, binaries, `MOBILEBUILDMCP_*` env vars, `.mobilebuildmcp/config.yaml` and the registry name `io.github.getsentry/mobilebuildmcp` **[Source]** ([CHANGELOG](https://github.com/getsentry/MobileBuildMCP/blob/main/CHANGELOG.md)). It needs macOS 14.5+, Xcode 16.x+ and Node 18+, works without Xcode running, and installs with `brew tap getsentry/xcodebuildmcp && brew install mobilebuildmcp` or `claude mcp add MobileBuildMCP -- npx -y mobilebuildmcp@latest mcp` ([README](https://github.com/getsentry/MobileBuildMCP/blob/main/README.md); [clients.mdx](https://github.com/getsentry/xcodebuildmcp.com/blob/main/app/docs/_content/clients.mdx)). Its 70-plus tools are grouped into workflows (`simulator`, `device`, `debugging` with `debug_attach_sim`/`debug_lldb_command`, `ui-automation` with `tap`/`key_press`/`snapshot_ui`/`screenshot`, `swift-package`, `coverage`, `xcode-ide`), of which "Only simulator workflow tools are enabled by default" because "Every advertised tool consumes context tokens in your agent" ([SKILL.md](https://github.com/getsentry/MobileBuildMCP/blob/main/skills/mobilebuildmcp/SKILL.md); [workflows.mdx](https://github.com/getsentry/xcodebuildmcp.com/blob/main/app/docs/_content/workflows.mdx)). Two operational facts matter: the skill instructs "Call `session_show_defaults` before the first build/run/test action in a session," and 2.7.0 changed the default so an omitted `configuration` "now follows the scheme instead of defaulting to Debug" ([CHANGELOG](https://github.com/getsentry/MobileBuildMCP/blob/main/CHANGELOG.md)). Since 2.7.0 its "UI automation tools now work fully with Xcode 27 simulators through Device Hub," it supports tvOS across its device and clean tools, and its `xcode-ide` workflow can proxy Apple's `mcpbridge` for "Preview rendering, Issue Navigator queries, Documentation search, Project Navigator operations" ([xcode-ide.mdx](https://github.com/getsentry/xcodebuildmcp.com/blob/main/app/docs/_content/xcode-ide.mdx)). A practitioner summary of the division of labor: "Raw xcodebuild closes the compilation loop. XcodeBuildMCP closes the runtime loop" **[Snippet]** ([tatejennings.com](https://www.tatejennings.com/blog/making-claude-code-work-for-ios-development)).

The third layer is small and compiler-adjacent: idb-based simulator servers such as ios-simulator-mcp (`claude mcp add ios-simulator npx ios-simulator-mcp`, Node 20+, versions below 1.3.3 had command-injection vulnerabilities) ([ios-simulator-mcp README](https://github.com/joshuayoes/ios-simulator-mcp)), and Anthropic's own `swift-lsp` plugin (`/plugin install swift-lsp@claude-plugins-official`), which gives go-to-definition, find-references, call hierarchies and, most usefully, "After each file edit, it automatically reports type errors and warnings" — but only in terminal sessions, not cloud ones, and only for `.swift` with no `.xcodeproj` build-server guidance in its README **[Official]** ([Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence); [Tools reference](https://code.claude.com/docs/en/tools-reference); [swift-lsp README](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/swift-lsp/README.md)). Anthropic's Claude Code Desktop added an iOS Simulator pane in public beta during July–September 2026, per press coverage **[Secondhand]** ([9to5Mac](https://9to5mac.com/2026/07/21/claude-code-brings-live-ios-app-testing-into-its-mac-app/)).

### tvOS: focus-engine debugging an agent can run headlessly

No first-hand Claude Code account for tvOS exists from any named engineer or company, so this subsection composes Apple-verified primitives **[Official]** into an agent loop **[Inference]**. Apple's two focus-debugging tools are the launch argument and the lldb class: "select Edit Scheme and add `-UIFocusLoggingEnabled YES` to the Arguments Passed On Launch section … the debugger logs all focus events," and `po UIFocusDebugger.status()` "returns the state of the focus engine" ([Debugging focus issues in your app](https://developer.apple.com/documentation/uikit/debugging-focus-issues-in-your-app)). `UIFocusDebugger` (tvOS 11+) is used only from lldb and offers `help()`, `status()`, `checkFocusability(for:)` ("Returns information about whether the item can become focused, including any known issues"), `focusGroups(for:)`, `preferredFocusEnvironments(for:)` and `simulateFocusUpdateRequest(from:)` ([UIFocusDebugger](https://developer.apple.com/documentation/uikit/uifocusdebugger)). Real output looks like `The following issues were found that would prevent this item from being focusable: - ISSUE: This item is not visible onscreen.`, which in the reported case traced to a zero-frame view in a second `UIWindow` ([Apple Developer Forums 751311](https://developer.apple.com/forums/thread/751311)). The engine's rules explain most bugs an agent will meet: "Only the focus engine can explicitly update focus, meaning there's no API for directly setting the focused item," a failed move broadcasts `movementDidFailNotification`, and the root view controller's `preferredFocusEnvironments` seeds initial focus ([About focus interactions for Apple TV](https://developer.apple.com/documentation/uikit/about-focus-interactions-for-apple-tv)). The fixes are `UIFocusGuide` ("an invisible, focusable region that can redirect focus movement") in UIKit and `focusSection()` (tvOS 15+; "If the modified view has no focusable descendants, then the modifier does nothing"), `focusable(_:interactions:)` (tvOS 17+) and `@FocusState` in SwiftUI ([UIFocusGuide](https://developer.apple.com/documentation/uikit/uifocusguide); [focusSection()](https://developer.apple.com/documentation/swiftui/view/focussection()); [FocusState](https://developer.apple.com/documentation/swiftui/focusstate)). A third-party tvOS skill's observation that `.disabled()` "breaks tvOS navigation entirely" is consistent with these rules but unverified ([mcpmarket tvOS focus skill](https://mcpmarket.com/tools/skills/tvos-focus-engine-assistant)).

Driving the remote has three documented paths. In UI tests, `XCUIRemote.shared.press(.select)` (Xcode 16.3+) sends "a momentary press of a button on a physical remote control," with buttons `up, down, left, right, select, menu, playPause, home, pageUp, pageDown, guide, fourColors, oneTwoThree, tvProvider`; swipes cannot be simulated ([XCUIRemote](https://developer.apple.com/documentation/xcuiautomation/xcuiremote); [XCUIRemote.Button](https://developer.apple.com/documentation/xcuiautomation/xcuiremote/button); [forum 651096](https://developer.apple.com/forums/thread/651096)). In the simulator, Device Hub maps arrow keys to focus movement, Return to "Trigger the action for the current focus," and Escape to "Move up one level in the navigation hierarchy" ([Interacting with your app in Device Hub](https://developer.apple.com/documentation/xcode/interacting-with-your-app-in-device-hub)). Xcode 27 removed the virtual Siri Remote, and one developer found focus stuck on a custom button that overrode `pressesBegan:withEvent:` without calling `super` until the call was added ([forum 844234](https://developer.apple.com/forums/thread/844234)); Device Hub also accepts keyboard input only for tvOS 18.0+ simulators ([Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)). For scripted input from an external agent, facebook/idb's `main` branch (commit dated 2026-10-08) added `idb ui remote up|down|left|right|select|menu`, "keyboard-backed" HID usages `{"up": 0x52, "down": 0x51, "left": 0x50, "right": 0x4F, "select": 0x28, "menu": 0x29}` that "the tvOS focus engine consumes" **[Source]** ([idb hid.py](https://github.com/facebook/idb/blob/main/idb/cli/commands/hid.py)); whether this is in a tagged release is unknown. The same codes, in decimal (82/81/80/79/40/41), can be sent through MobileBuildMCP's `key_press` tool, which documents "40 Return/Enter" among common values **[Inference]** ([key_press.ts](https://github.com/getsentry/MobileBuildMCP/blob/main/src/mcp/tools/ui-automation/key_press.ts)). A headless focus probe that composes the documented lldb batch flags with Apple's `po` form is therefore **[Inference]**:

```bash
# Build, install, launch with focus logging, capture the focus-engine log, then ask the engine
xcrun simctl launch --console-pty booted com.example.tvapp -UIFocusLoggingEnabled YES &
xcrun simctl spawn booted log stream --predicate 'process == "TVApp"' --style compact > /tmp/focus.log &
xcrun lldb --batch -n TVApp \
  -o "expr -l Swift -- import UIKit" \
  -o "po UIFocusDebugger.status()" \
  -o "process detach"
```

`lldb --batch` "Tells the debugger to run the commands from -s, -S, -o & -O, and then quit," `-n` attaches by name and `-w` waits for launch ([lldb(1)](https://keith.github.io/xcode-man-pages/lldb.1.html)); the `import UIKit` step is our assumption. On-device debugging floors are tvOS 15 for Xcode 26.3 and tvOS 17 for Xcode 27 ([Xcode 26.3 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_3-release-notes); [Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)).

### Headless debugging and the four tactics for a slow native loop

Crash triage has a fully documented command path **[Official]**: crash files must have the `.crash` or `.ips` extension; `xcrun crashlog <file>` "is a shortcut to invoke a Python module that supports parsing and symbolicating crash reports"; `python3 CrashSymbolicator.py <report> -d <dSYM>` in `CoreSymbolicationDT.framework/Resources` "supports JSON-format crash reports and inlined frames"; and `atos -arch arm64 -o App.app.dSYM/Contents/Resources/DWARF/App -l <load-address> -i <addr>` symbolicates single frames ([Adding identifiable symbol names to a crash report](https://developer.apple.com/documentation/xcode/adding-identifiable-symbol-names-to-a-crash-report)). Unified logging is read with `log stream --predicate '…' --process <name>` and `--last 2m` ([log(1)](https://keith.github.io/xcode-man-pages/log.1.html)), and profiling with `xcrun xctrace record --template 'Time Profiler' --time-limit 60s --output /tmp/App.trace --launch -- /path/App.app` followed by `xctrace export --input … --xpath '/trace-toc/run[@number="1"]/data/table[@schema="time-profile"]'`, with Steinberger's skill warning that the exported XML is huge and must be XPath-filtered, never printed ([xctrace(1)](https://keith.github.io/xcode-man-pages/xctrace.1.html); [steipete/agent-scripts](https://github.com/steipete/agent-scripts/blob/main/skills/instruments-profiling/SKILL.md)); Xcode 27 fixed `xctrace record` never starting for simulator targets ([Xcode 27 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)).

The slow-loop tactics converge across sources. First, build at checkpoints: "xcodebuild is much slower than a web project's build, so an agent that builds after every tiny edit will feel sluggish. Have it build at meaningful checkpoints, not on every line" **[Snippet]** ([spaceport.build](https://spaceport.build/blog/claude-code-ios-development)). Second, shrink the inner loop: Justin Searls measured a new app's `xcodebuild test` at "over 25 seconds on my M4 MacBook Pro" and got `swift test` to ~0.4 s ("over 60 times faster") by moving app code into a Swift package, motivated by a hook that runs tests after each edit **[Snippet]** ([justin.searls.co](https://justin.searls.co/posts/i-made-xcodes-tests-60-times-faster/)); the official CLAUDE.md sample line "Prefer running single tests, and not the whole test suite, for performance" says the same ([Best practices](https://code.claude.com/docs/en/best-practices)). Third, preserve DerivedData and filter output, as Trott does ([twocentstudios](https://twocentstudios.com/2025/12/27/closing-the-loop-on-ios-with-claude-code/)). Fourth, close the runtime loop with the simulator tools above; Anthropic's sanctioned way to teach Claude how to launch an Xcode app is the `/run-skill-generator` skill, which writes a per-project skill for `/run` and `/verify` ("Confirm a code change does what it should by building your project's app, running it, and observing the result") ([Commands](https://code.claude.com/docs/en/commands)).

## Objective 3: advisory context plus deterministic hooks prevent architectural regressions

### CLAUDE.md is context, not configuration, and must stay under 200 lines

The single most important sentence for governance is in the memory docs: "Claude treats CLAUDE.md files as context, not enforced configuration… To block an action regardless of what Claude decides, use a PreToolUse hook instead" **[Official]** ([Memory](https://code.claude.com/docs/en/memory)). Files load in order from managed policy (`/Library/Application Support/ClaudeCode/CLAUDE.md` on macOS) through `~/.claude/CLAUDE.md`, `./CLAUDE.md` or `./.claude/CLAUDE.md`, and the gitignored `./CLAUDE.local.md`; all are "concatenated into context rather than overriding each other," and subdirectory files load lazily only when Claude reads, writes or edits a file there. The size rule is explicit: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence," and `@path` imports "don't reduce its context cost, because imported files also load at launch." The best-practices page's include list is "Bash commands Claude can't guess," "Testing instructions and preferred test runners," "Repository etiquette," "Architectural decisions specific to your project" and "Developer environment quirks"; its exclude list is "Anything Claude can figure out by reading code" and "Standard language conventions Claude already knows," with the test "Would removing this cause Claude to make mistakes?" and the warning that "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" ([Best practices](https://code.claude.com/docs/en/best-practices)). Anthropic's June 2026 steering guide formalizes ownership ("Keep CLAUDE.md under 200 lines, assign an owner, and review changes like code") and the split of mechanisms ("Absolute prohibitions → hooks or permissions, not instructions"), rating root CLAUDE.md context cost "High" against "Low" for skills, subagents and hooks ([Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)). Maintenance tooling exists: `/init` (with `CLAUDE_CODE_NEW_INIT=1` for a reviewable proposal covering skills and hooks), `/memory`, `/context` to confirm which files loaded, and, from v2.1.283, `/doctor prompt-audit`, which "looks for problems such as instructions written for older models, references to files or commands that don't exist, and files that contradict each other" ([Memory](https://code.claude.com/docs/en/memory)). Anthropic's managed Code Review "reads your repository's `CLAUDE.md` files and treats newly introduced violations as nit-level findings," which makes CLAUDE.md double as review policy ([Code review](https://code.claude.com/docs/en/code-review)).

The best real Swift example is tomada1114/ios-template, whose `CLAUDE.md` is the single line `@AGENTS.md` so one file serves Claude Code and Codex **[Source]** ([ios-template CLAUDE.md](https://github.com/tomada1114/ios-template/blob/main/CLAUDE.md)). Its `AGENTS.md` holds only "what every agent needs before it knows which task it is on: what the app is, how to check a change, where code goes, and which decisions need a human," pushing per-change conventions to skills and "a value a gate enforces" to the gate's config. Concretely it carries a `just` quick reference (`just build`, `just test`, `just lint`, `just check # Run all checks: verify-hooks → fmt → lint → test-scripts → check-harness → test → build`), a "Validating a change" table mapping "What you changed" to "The narrowest check that can fail," the one-way dependency diagram ("Core ← UI and Core ← Platform, both ← App. `MyAppUI` and `MyAppPlatform` are siblings and never import each other"), "`MyApp.xcodeproj` is generated — edit `project.yml` instead," and a "Security and human approval" list: never read `.env`, `*.p12`, `*.mobileprovision` or `GoogleService-Info.plist`; sign-off before touching entitlements, release tags, new dependencies, or "Weakening any gate… `// swiftlint:disable`… `@unchecked Sendable`… `git commit --no-verify`"; and "Working around a denied command. Re-spelling it (`git -C . …`, `bash -c '…'`…) is forbidden. Stop and ask" ([ios-template AGENTS.md](https://github.com/tomada1114/ios-template/blob/main/AGENTS.md)). The practitioner rulebooks of Wals, Bartlett (who logs Swift 6.2 concurrency warnings so they do not recur) and Karunaratne (SwiftUI-first, Swift 6 async/await/actors) follow the same growth rule **[Snippet]** ([donnywals.com](https://www.donnywals.com/setting-up-a-delivery-pipeline-for-your-agentic-ios-projects/); [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/the-year-swiftui-died)), and Steinberger's curated `docs/swift-concurrency.md`, referenced from CLAUDE.md "whenever it writes Swift," is the canonical mitigation for the concurrency weakness ([x.com/steipete](https://x.com/steipete/status/1937816669075689840)).

### Path-scoped rules describe a boundary and name the gate that enforces it

`.claude/rules/*.md` arrived in Claude Code 2.0.64 ([CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Rules without `paths:` frontmatter "are loaded at launch with the same priority as `.claude/CLAUDE.md`"; rules with `paths:` globs "trigger when Claude uses the Read, Write, or Edit tool on a file matching the pattern"; "`paths` is the only field Claude Code reads from a rule"; unparseable YAML silently loads the rule unscoped, visible only with `claude --debug` **[Official]** ([Memory](https://code.claude.com/docs/en/memory)). Two consequences follow. A rule about `*.pbxproj` loads only when Claude touches that file, which is too late to prevent the edit, so prevention belongs in a hook or an `Edit(**/*.pbxproj)` deny rule **[Inference]**. And because two community reports describe path-scoped rules silently not loading (#17204 on WSL2, #22170 on macOS 2.1.27), a team should verify with `/context` after touching a matching file ([anthropics/claude-code#17204](https://github.com/anthropics/claude-code/issues/17204)). ios-template's rule files show the pattern worth copying: `swift.md` (paths `Packages/**/*.swift`, `App/**/*.swift`) states "`MyAppCore` must never import SwiftUI, UIKit, AppKit, … or WidgetKit … (enforced by `.swiftlint.yml`'s `no_ui_import_in_core` and `ArchitectureBoundaryTests`)," "No `@unchecked Sendable` without a comment proving the invariant it papers over," and "`os.Logger` is the only logging facility. NEVER `print`"; `project.md` (paths `project.yml`, `Package.swift`, `Package.resolved`, `.swiftlint.yml`, `Config/*.xcconfig`) says "NEVER lower a coverage floor" and "NEVER remove SwiftLint rules without explicit user approval"; `testing.md` requires "Swift Testing only (`@Test`, `#expect`, `#require`, `@Suite`)," "Fakes, not mocks," and "NEVER weaken an assertion to make a test pass" **[Source]** ([swift.md](https://github.com/tomada1114/ios-template/blob/main/.claude/rules/swift.md); [project.md](https://github.com/tomada1114/ios-template/blob/main/.claude/rules/project.md); [testing.md](https://github.com/tomada1114/ios-template/blob/main/.claude/rules/testing.md)). The issue that introduced them records why: "without them it re-derives 'where does a test go' and 'may Core import SwiftData' every time" ([ios-template#5](https://github.com/tomada1114/ios-template/issues/5)). A tvOS rule composed on the same syntax **[Inference]**:

```markdown
---
paths:
  - "**/tvOS/**/*.swift"
  - "**/*+tvOS.swift"
---
# tvOS focus and input
- Every interactive view must be reachable with the Siri Remote: verify `focusable`/`@FocusState`
  paths and `.focusSection()` grouping; never rely on tap gestures.
- Use `#if os(tvOS)` for tvOS-only APIs; shared files must compile for iOS and tvOS
  (`xcodebuild build -scheme App-tvOS -destination 'generic/platform=tvOS Simulator' -quiet`).
```

### Hooks are the deterministic layer, and exit code 2 is the only one that blocks

The hooks reference lists 33 events, five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`), and the exit-code contract: "2: blocking error. Stderr is the reason… blocks a `PreToolUse` call, rejects a prompt, prevents `Stop`," while "Other: non-blocking error. The action proceeds," with an explicit warning that "exit 1 does not block, so enforcement hooks should use `exit 2`" **[Official]** ([Hooks reference](https://code.claude.com/docs/en/hooks)). Hook stdin is JSON with `tool_name`, `tool_input`, `cwd`, `permission_mode` and, for `Stop`, `stop_hook_active`, which "is `true` when Claude Code is already continuing as a result of a stop hook" and must be checked "to avoid blocking on a condition that will never resolve"; an 8-consecutive-continuation cap applies. The `if: "Bash(git push *)"` filter is "best-effort," so "use the permission system rather than a hook to enforce a hard allow or deny" ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). The official examples are a `PostToolUse` formatter on `Edit|Write`, a `PreToolUse` `protect-files.sh` that exits 2 for `.env`, lockfiles and `.git/`, a `SessionStart` hook with matcher `compact` to re-inject context after compaction, and `prompt`/`agent` Stop hooks that return `{"ok": false, "reason": …}` ([Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Hooks reference](https://code.claude.com/docs/en/hooks)). Two security facts shape how a team ships hooks: "a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted," which is why `--bare` is recommended for scripts ([Headless](https://code.claude.com/docs/en/headless)), and Steinberger's reminder that "models will get around a hook if they're determined to" means hooks catch what Claude normally writes while the sandbox and CI remain the backstop ([steipete.me](https://steipete.me/posts/just-talk-to-it)).

The real Swift formatter in ios-template encodes the one detail most community examples get wrong: it exits 2 on failure "because Claude Code feeds a PostToolUse hook's stderr back to the agent only on exit 2," formats only the single edited `.swift` file, and bails out for paths outside the repo **[Source]** ([format-edited-file.sh](https://github.com/tomada1114/ios-template/blob/main/scripts/format-edited-file.sh)); by contrast a widely shared SwiftLint hook "sends errors to `/dev/null` and never exits 2, so Claude would not see violations" ([community summary](https://blog.vincentqiao.com/en/posts/claude-code-settings-hooks/)). The composed hook set for an iOS/tvOS repo **[Inference]**, with scripts in the playbook's `.claude/hooks/`:

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit|Write|MultiEdit",
        "hooks": [ { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-project-files.sh" } ] },
      { "matcher": "Bash",
        "hooks": [ { "type": "command", "if": "Bash(git push *)", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-force-push.sh" } ] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write|MultiEdit",
        "hooks": [ { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/lint-swift-file.sh", "timeout": 120 } ] }
    ],
    "SessionStart": [
      { "matcher": "compact",
        "hooks": [ { "type": "command", "command": "echo 'Reminder: build with xcodebuild -quiet via xcbeautify -qq; run the narrowest test; never edit .pbxproj; see AGENTS.md'" } ] },
      { "hooks": [ { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/session-status.sh" } ] }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/stop-gate.sh", "timeout": 900 } ] }
    ]
  }
}
```

The playbook ships this hook set under the names `protect-files.sh`, `guard-bash.sh` (which inspects every Bash command rather than relying on an `if` filter), `format-swift.sh`, `session-start.sh` and `stop-gate.sh`; the example names above are the report's own shorthand.

```bash
#!/bin/bash
# .claude/hooks/protect-project-files.sh  (PreToolUse; exit 2 = block, stderr reaches Claude)
INPUT=$(cat); FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
case "$FILE_PATH" in
  *.pbxproj|*.xcworkspacedata|*/Podfile.lock|*/Package.resolved|*.xcconfig|*.entitlements|*.mobileprovision)
    echo "Blocked: $FILE_PATH is a generated or locked project file. Edit project.yml (XcodeGen) or ask a human." >&2
    exit 2 ;;
esac
exit 0
```

```bash
#!/bin/bash
# .claude/hooks/stop-gate.sh  (Stop; unit tests must pass before the turn ends; respects the loop guard)
INPUT=$(cat)
[ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ] && exit 0
cd "$CLAUDE_PROJECT_DIR" || exit 0
if ! swift test --package-path Packages/AppKit 2>&1 | tail -n 40 >&2; then   # narrow, fast gate
  echo "Unit tests failed; fix them before finishing." >&2; exit 2
fi
exit 0
```

A `Stop` gate that runs full `xcodebuild test` is tolerable only if the inner test target is small; the Searls package-extraction timing is what makes a sub-second gate possible, and the `agent` hook type (default 60 s timeout, up to 50 turns) is the documented alternative for a verifying subagent ([Hooks reference](https://code.claude.com/docs/en/hooks)).

### Permissions and the sandbox close the holes that text matching leaves open

Settings precedence is managed → `--settings` → `.claude/settings.local.json` → `.claude/settings.json` → `~/.claude/settings.json` **[Official]** ([Settings](https://code.claude.com/docs/en/settings)). Rules are `Tool` or `Tool(specifier)` with deny > ask > allow; `Bash(ls *)` matches `ls -la` but not `lsof`, `Bash(ls*)` matches `lsof`, compound commands are checked per subcommand, and the documented limits are sobering: `Bash(rm *)` stops `rm -rf build/` but not `/bin/rm -rf build/` or `bash -c 'rm -rf build/'`, and `Bash(git push *)` does not stop `git -C . push origin main` ([Permissions](https://code.claude.com/docs/en/permissions)). Deny rules "block in every mode, including `bypassPermissions`," and `Read(./.env)` stops file tools and `cat .env` "but not `grep -r` run over the directory; the `sandbox` block … closes that gap" ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Settings example](https://code.claude.com/docs/en/settings-example)). The sandbox "is a boundary that the operating system enforces around the shell commands Claude runs" (Seatbelt on macOS), "covers shell commands only," is off by default, and in strict form (`allowUnsandboxedCommands: false`, `failIfUnavailable: true`) becomes admin-required when the unsandboxed retry is disabled in managed settings ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Enterprise governance lives in `managed-settings.json` (`/Library/Application Support/ClaudeCode/`), deliverable via the `com.anthropic.claudecode` MDM profile, with `allowManagedPermissionRulesOnly`, `disableBypassPermissionsMode`, `disableAutoMode`, `allowManagedHooksOnly`, an MCP allowlist and `requiredMinimumVersion` ([Managed settings](https://code.claude.com/docs/en/managed-settings)). ios-template deliberately ships no committed permission list, treating allow rules as personal (`settings.local.json`) and gates as CI; the composed team settings below therefore commit only `deny`/`ask` plus a minimal build allowlist **[Inference]** (the caveat from the docs stands: `Bash(git push --force *)` matches only that spelling):

```json
{
  "permissions": {
    "allow": ["Bash(xcodebuild build *)", "Bash(xcodebuild test *)", "Bash(xcodebuild -list *)",
              "Bash(xcrun simctl *)", "Bash(swift build *)", "Bash(swift test *)",
              "Bash(swiftlint *)", "Bash(swiftformat *)", "Bash(xcodegen *)",
              "Bash(git diff *)", "Bash(git log *)", "Bash(git status *)", "mcp__MobileBuildMCP__*"],
    "ask":   ["Bash(git push *)", "Bash(pod install *)", "Bash(swift package update *)",
              "Bash(xcrun altool *)", "Bash(xcrun notarytool *)", "Bash(fastlane *)"],
    "deny":  ["Edit(**/*.pbxproj)", "Edit(**/*.xcworkspacedata)", "Edit(**/Podfile.lock)", "Edit(**/Package.resolved)",
              "Edit(**/*.entitlements)", "Edit(**/*.xcconfig)",
              "Read(./.env)", "Read(./.env.*)", "Read(**/*.p12)", "Read(**/*.p8)", "Read(**/*.mobileprovision)",
              "Read(**/GoogleService-Info.plist)", "Bash(git push --force *)", "Bash(git push -f *)",
              "Bash(rm -rf *)", "Bash(curl *)", "Bash(wget *)"],
    "defaultMode": "acceptEdits"
  },
  "sandbox": { "enabled": true, "network": { "allowedDomains": ["github.com", "*.apple.com", "swiftpackageindex.com"] } }

```

### Skills, subagents and MCP servers are capabilities you govern, not instructions you hope for

Since v2.1.3 "Custom commands have been merged into skills": `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`, and skills add supporting files, `allowed-tools` ("Tools Claude can use without asking permission during the turn that invokes this skill"), `context: fork`, and `disable-model-invocation: true` for "workflows you want to trigger manually" **[Official]** ([Skills](https://code.claude.com/docs/en/skills)). The `` !`cmd` `` syntax injects live shell output into the skill body before Claude sees it, which is how a `/build-and-test` skill can embed `xcrun simctl list devices available`. Side-effecting iOS workflows (release, TestFlight upload, `pod install`) should carry `disable-model-invocation: true` and a narrow `allowed-tools` list **[Inference]**; ios-template's catalogue (`tdd`, `create-pr`, `smart-commit`, `changing-gates`, `running-the-app` with dark-mode and large-Dynamic-Type screenshots, `localizing-the-app`, `shipping-issues`) is a proven shape ([ios-template AGENTS.md](https://github.com/tomada1114/ios-template/blob/main/AGENTS.md)). Subagents are Markdown with frontmatter (`name`, `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `memory`, `isolation: worktree`), run in a fresh context containing "Its own system prompt … The task message … CLAUDE.md files … A git status snapshot," and up to 20 run concurrently ([Subagents](https://code.claude.com/docs/en/sub-agents)). Because they inherit CLAUDE.md but not path-scoped rules until they read a matching file, a reviewer prompt should restate the critical layering rules, and an "architecture guardian" is most reliable as a read-only agent (`disallowedTools: Edit, Write`) running deterministic tools, with the same check repeated in CI **[Inference]**. Official guidance endorses the fresh-context reviewer because "Claude won't be biased toward code it just wrote" ([Best practices](https://code.claude.com/docs/en/best-practices)). Project MCP servers live in a committed `.mcp.json` with `${VAR}`/`${VAR:-default}` expansion in `command`, `args`, `env`, `url` and `headers`; interactive sessions prompt before using them, but `-p`, SDK and cloud sessions "load project-scoped servers without asking" (mitigate with `--strict-mcp-config` or `disabledMcpjsonServers`); tools are permissioned as `mcp__<server>__<tool>` with allow globs like `mcp__MobileBuildMCP__*` ([MCP](https://code.claude.com/docs/en/mcp)). Enterprises can lock this to an approved catalog with `allowedMcpServers` entries of the form `{ "serverCommand": ["npx","-y","mobilebuildmcp@latest","mcp"] }` plus `allowManagedMcpServersOnly: true` ([Managed MCP](https://code.claude.com/docs/en/managed-mcp)).

### Enforce every boundary twice and let CI be the backstop

The strongest regression-prevention pattern found enforces each architectural rule with two different tools on two different jobs. ios-template's `.swiftlint.yml` runs `strict: true`, `opt_in_rules: [all]`, and a `custom_rules` regex `no_ui_import_in_core` (severity `error`) that forbids `import SwiftUI|UIKit|AppKit|Cocoa|SwiftData|CoreData|CloudKit|…` inside `Packages/MyAppKit/Sources/MyAppCore/`, handling `@preconcurrency` and `import struct SwiftUI.Color` forms **[Source]** ([ios-template .swiftlint.yml](https://github.com/tomada1114/ios-template/blob/main/.swiftlint.yml)). A Swift Testing suite, `ArchitectureBoundaryTests`, is "The second enforcement of the module boundaries": "the lint rule runs in the `lint` job and the pre-commit hook, this suite in the `test` job, so removing either one still leaves the other catching a regression," and it additionally bans Foundation types "an adapter owns (`URLSession`, `UserDefaults`)" that no import ban can see ([ArchitectureBoundaryTests.swift](https://github.com/tomada1114/ios-template/blob/main/Packages/MyAppKit/Tests/MyAppCoreTests/ArchitectureBoundaryTests.swift)). This matters for agents specifically because a regex lint rule can be silenced by a `// swiftlint:disable` the agent writes; AGENTS.md forbids that without sign-off, and the test-side check still fails CI **[Inference]**. Alternatives exist for layer rules: `solid-like-a-rock` parses imports with SwiftSyntax, generates `.solid.yml` from the real graph with `--freeze`, fails with `layer 'Presentation' must not import 'Data'`, and advertises Claude Code integration "since the guardrail lives in the build" ([solid-like-a-rock](https://github.com/nenadvulic/solid-like-a-rock)); `architecture-lint` adds a ratchet baseline that fails "only on regressions" ([architecture-lint](https://github.com/OrenSegal/architecture-lint)). SwiftLint analyzer rules (`unused_import`, `unused_declaration`, `capture_variable`) need a compiler log (`swiftlint analyze --compiler-log-path xcodebuild.log`) and belong in CI, not hooks ([SwiftLint README](https://github.com/realm/SwiftLint); [UnusedImportRule.swift](https://github.com/realm/SwiftLint/blob/main/Source/SwiftLintBuiltInRules/Rules/Lint/UnusedImportRule.swift)). Two tool-status facts affect planning: Periphery's open-source repository is archived because "Periphery has become a commercial product" ([periphery README](https://github.com/peripheryapp/periphery)), and `danger-swiftlint` is deprecated because SwiftLint support "is now built into Danger Swift" (`SwiftLint.lint(inline: true)`) ([danger-swiftlint README](https://github.com/ashfurrow/danger-swiftlint/blob/master/README.md)). The agent-facing loop is therefore: the path-scoped rule *tells* Claude the boundary, the PostToolUse hook *runs* the single-file lint on every edit, a Stop hook or `/code-review` *verifies* before the turn ends, and CI *gates* the PR **[Inference]**.

### Automated review in three layers

The official GitHub Action gives the cheapest robust setup. The `code-review` plugin workflow runs on `pull_request` with `plugin_marketplaces: "https://github.com/anthropics/claude-code.git"`, `plugins: "code-review@claude-code-plugins"`, `prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"` and `claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'`, where that `--allowedTools` line must be kept "because the Claude Code GitHub Action starts the MCP server that posts inline comments only when `--allowedTools` in `claude_args` names it"; drafts, trivial PRs and fork PRs (no secrets) are skipped **[Official]** ([GitHub Actions](https://code.claude.com/docs/en/github-actions)). The `pr-review-filtered-paths.yml` example triggers on `paths:` globs and should be swapped to `**/*.swift`, `**/project.yml` and `**/Package.swift` ([claude-code-action examples](https://github.com/anthropics/claude-code-action/blob/main/examples/pr-review-filtered-paths.yml)); cost controls are `--max-turns` in `claude_args`, workflow timeouts and concurrency. Locally, `/code-review [low…max] [--fix] [--comment] [--max-findings n]` reviews "your branch's commits ahead of its upstream plus any uncommitted changes," follows CLAUDE.md, runs as a background subagent, and escalates to a cloud `ultrareview`; `/security-review` checks the diff against origin's default branch for injection, auth and data-exposure issues ([Code review](https://code.claude.com/docs/en/code-review); [Commands](https://code.claude.com/docs/en/commands)). Anthropic's managed Code Review service (Team/Enterprise research preview) averages "$15-25" per review, always completes its check run "with a neutral conclusion" so merge gating must parse the `bughunter-severity:` JSON yourself, and is tuned by a `REVIEW.md` with "What Important means here," "Cap the nits," "Do not report" (anything CI already enforces) and "Always check" sections ([Code review](https://code.claude.com/docs/en/code-review)). A headless review script that returns machine-readable findings is **[Inference]** on documented flags:

```bash
# scripts/claude-review.sh <pr-number>   — headless, bare, bounded, structured
gh pr diff "$1" | claude --bare -p \
  --output-format json --max-turns 4 --max-budget-usd 3 --permission-mode dontAsk \
  --append-system-prompt "$(cat REVIEW.md)" \
  --json-schema '{"type":"object","properties":{"blocking":{"type":"array","items":{"type":"string"}},"nits":{"type":"array","items":{"type":"string"}}},"required":["blocking","nits"]}' \
  | jq '.structured_output'
```

`REVIEW.md` should name the Swift defect classes the official language-agnostic prompts omit: non-`Sendable` values crossing actors and `@unchecked Sendable` without proof, retain cycles in long-lived closures and Combine sinks, heavy work in SwiftUI `body`, tvOS views unreachable by focus, and `Features/` importing `Networking`/`Persistence` **[Inference]**.

## Objective 4: a four-phase adoption plan sequences the playbook by payoff and risk

The copy-in deliverable lives at `playbook/` and contains a `CLAUDE.md` template, `.claude/rules`, `.claude/settings.json` with hooks, `.claude/skills`, `.claude/agents`, `.mcp.json`, `scripts/` and `ci/`. Every file there is **[Inference]**-tier until the team runs it: the syntax is from official documentation and the patterns from ios-template and MobileBuildMCP, but none of the composed artifacts has been executed against a real Xcode project, and simulator names, scheme names and package paths are placeholders. The plan below orders adoption so that the cheapest, highest-leverage, lowest-risk pieces land first and the pieces that need a running Xcode, a macOS CI runner or a legal decision land last.

Phase 0 is a half-day of prerequisites. Pin Claude Code at or above 2.1.293 so path-scoped rules fire on writes, install `xcbeautify` and `xcsift` (`brew install xcbeautify xcsift`), install the `swift-lsp` plugin, add `.claude/worktrees/`, `.derivedData/` and `.spm/` to `.gitignore`, write a `.worktreeinclude` for local xcconfig and `.xcode.env`, and run `xcodebuild -list` and `xcrun simctl list devicetypes` once to capture the real scheme and device names into the CLAUDE.md template. Commit the `deny` and `ask` blocks of `.claude/settings.json` immediately; they "apply in every session, trusted or not," cost nothing, and remove the two highest-consequence failure classes (project-file corruption and secret reads) before anyone depends on prose ([Settings example](https://code.claude.com/docs/en/settings-example)).

Phase 1 (week 1) is context and prevention. Replace or trim `CLAUDE.md` to under 200 lines using the template's structure (build and test commands with exact iOS and tvOS destinations, the layer diagram, the narrowest-check table, the ask-a-human list), move Swift, testing, project-file and tvOS conventions into `.claude/rules/`, install the `protect-project-files.sh` PreToolUse hook and the single-file `lint-swift-file.sh` PostToolUse hook, and set `defaultMode: plan` for the first week so engineers learn the explore-plan-implement rhythm before auto-accepting edits. Adopt the session discipline immediately: one task per `claude -n <name> -w <name>` session, `/compact Focus on …` after each green build, `/clear` once the PR is open, a `PLAN.md`/`SPEC.md` in the worktree so a fresh session or reviewer subagent can pick up without the transcript. Run `/doctor prompt-audit` at the end of the week and delete anything Claude already did correctly without being told.

Phase 2 (week 2) is procedure and verification. Add the playbook's skills (`build`, `test`, `run-sim`, `triage-crash`, `tvos-focus-debug`, `review-pr`, `release-check`; the side-effecting `release-check` carries `disable-model-invocation: true`), the `swift-reviewer`, `swift-test-writer` and `architecture-guardian` subagents, the `SessionStart` compact re-injection hook, and a `Stop` gate scoped to the fastest test target. If the app's logic is not yet in a Swift package, this is the week to start extracting it, because every later gate's latency depends on `swift test` being sub-second rather than `xcodebuild test` being 25 seconds. Begin the writer/reviewer habit: implementation in session A, `Use the swift-reviewer subagent to review the diff against PLAN.md` in session B.

Phase 3 (week 3) is the runtime loop. Add `.mcp.json` with MobileBuildMCP (workflows `simulator,ui-automation`, plus `debugging` for the tvOS focus probe), and, on Xcode 26.3+, Apple's `xcrun mcpbridge` for previews and documentation search; pin `mobilebuildmcp@2.7.1` rather than `@latest` because 2.7.0 changed the configuration default. Teach `/verify` with `/run-skill-generator`, and write the tvOS focus recipe into a skill: build for `tvOS Simulator`, launch with `-UIFocusLoggingEnabled YES`, drive focus with `key_press` or `idb ui remote`, screenshot plus `snapshot_ui`, and `po UIFocusDebugger.status()` through `debug_lldb_command`. Only now add worktree parallelism in earnest, and only on separate schemes or packages, because each worktree pays a cold build.

Phase 4 (week 4) is review, gates and measurement. Install the filtered-paths GitHub Action for Swift files, add `scripts/claude-review.sh` for a structured second opinion, and move the twice-enforced architecture checks into `ci/` (SwiftFormat `--lint`, SwiftLint `--strict` with custom rules, `solid-like-a-rock`, the architecture test suite, a tvOS build, and SwiftLint analyzer rules on a fresh build log). Turn on OpenTelemetry (`CLAUDE_CODE_ENABLE_TELEMETRY=1`) so `claude_code.token.usage`, `claude_code.cost.usage` (attributed by `mcp_server.name` and `skill.name`) and `claude_code.tool_result` sizes are recorded from day one ([Monitoring usage](https://code.claude.com/docs/en/monitoring-usage)), pair Anthropic's contribution metrics with DORA metrics as its own blog recommends, and schedule the six-monthly CLAUDE.md/skills/hooks reset that Cherny describes. Phase 4 is also when the GitNexus A/B in Part 2 can run, because by then the team has the baseline arm (bare Claude Code plus `swift-lsp`) that the comparison requires.

## Part 2: GitNexus parses Swift but its license and evidence gap demand a local A/B

### What GitNexus is and how it hooks into Claude Code

GitNexus describes itself as "The context engine for Enterprise Codebases" that "Indexes any codebase into a knowledge graph — every dependency, call chain, cluster, and execution flow — then exposes it through smart MCP tools so AI agents never miss code" **[Source]** ([README](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)). Its pipeline is Tree-sitter parsing, import/call/heritage resolution "with language-aware logic," Leiden community clustering, "Processes" traced from entry points, and hybrid BM25-plus-semantic search, stored in an embedded LadybugDB under `.gitnexus/` with the repo registered in `~/.gitnexus/registry.json` ([ARCHITECTURE.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/ARCHITECTURE.md)). The "zero-server" tagline applies only to the WASM browser UI; the Claude Code path is a local Node MCP process. It exposes 19 MCP tools — `query`, `context` ("360-degree symbol view"), `impact` ("Blast radius analysis with depth grouping and confidence"), `trace`, `detect_changes` ("Git-diff impact"), `cypher`, `rename` (which mutates files), and others — plus MCP resources such as `gitnexus://repo/{name}/context` reporting stats and staleness ([README](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)). Integration is one command: `npx gitnexus analyze` "indexes the codebase, installs agent skills, registers Claude Code hooks, and creates `AGENTS.md` / `CLAUDE.md` context files," and `npx gitnexus setup` or `claude mcp add gitnexus -- npx -y gitnexus@latest mcp` registers the server. The Claude Code integration is rated "Full" because PreToolUse hooks on `Grep|Glob|Bash` "enrich the search before it runs" by injecting `additionalContext` with a 10-second timeout, and PostToolUse hooks on `Bash` "detect a stale index after commits" ([hooks.json](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus-claude-plugin/hooks/hooks.json)). Token cost therefore arrives through four channels: deferred MCP tool definitions, ~108 KB of `SKILL.md` across 11 skills (loaded on demand), a `CLAUDE.md` block designed to stay "under 120 lines," and hook context appended to every Grep, Glob and Bash call — the last being the channel most likely to bloat a long iOS debugging session in which every `xcodebuild` invocation is a Bash call **[Inference]** ([ai-context.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/cli/ai-context.ts); [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). No measurement of that overhead by the maintainers or anyone else was found.

### Swift and Objective-C support is present, heuristic, and silently skippable

Contrary to the brief's premise, the README's language table lists **16 languages including Swift, Objective-C, C and C++**, with Swift showing checkmarks for Exports, Heritage, Type Annotations, Constructor Inference, Config, Frameworks and Entry Points but *not* for Imports or Named Bindings, and Objective-C showing only Imports, Exports, Heritage and Type Annotations **[Source]** ([README](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)). The Swift provider is substantial: 18 source files covering receiver binding, SPM target grouping, implicit same-target visibility, `#if os(tvOS)`-style conditional-compilation preprocessing, Apple SDK module recognition (`Foundation, UIKit, SwiftUI, Combine, XCTest, Testing, Observation, os` …), and, since PR #3355, `project.pbxproj` parsing so that "Each Xcode native target compiles to its own Swift module," including Xcode 16 synchronized folders, with the stated limits that only `<group>` and `SOURCE_ROOT` paths resolve and `$(…)` build settings are not expanded ([xcode-project.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/core/ingestion/languages/swift/xcode-project.ts); [sdk-modules.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/core/ingestion/languages/swift/sdk-modules.ts)). Framework heuristics score a SwiftUI `@main` App at 3.0, `UIViewController` subclasses at 2.5 and SwiftUI views at 1.8 as entry points ([framework-detection.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/core/ingestion/framework-detection.ts)); nothing is tvOS-specific. The Objective-C provider is an explicit MVP that handles classes, protocols, categories, properties and "conservative static message sends," while "`id`, `Class`, macros, reflection, `performSelector:`, `NSInvocation`, runtime injection, or unknown type → Store selector/location with `resolution=unresolved`; do not emit a certain call edge" — so `impact` on Objective-C under-reports dynamically dispatched callers by design ([objective-c-provider.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/docs/languages/objective-c-provider.md)).

Three caveats determine whether any of that works on your machine. First, `tree-sitter-swift` is an *optional* vendored grammar that "can silently soft-fail when no prebuild matches the host platform" or is skipped by `GITNEXUS_SKIP_OPTIONAL_GRAMMARS=1`, in which case the only signal is one stderr line: `optional grammar "tree-sitter-swift" is unavailable — .swift files will not be parsed` ([optional-grammars.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/cli/optional-grammars.ts)). Second, Swift resolution bugs are being filed and fixed weekly: #3426, open on 30 September 2026, reports "Swift concrete-type extension calls resolve to unrelated same-name members," and #3425/#3434 (fixed 2 October) concerned injected closure properties resolving to unrelated methods — exactly the false-edge failure mode that will corrupt `impact` results for common Swift names like `configure()`, `update()` and `start()` ([issues?q=swift](https://github.com/abhigyanpatwari/GitNexus/issues?q=swift)). Third, the only published Swift benchmarks are internal regression baselines under `gitnexus/bench/`, not accuracy-versus-compiler studies, and the `context` resource reports only `files`, `symbols` and `processes` with no per-language breakdown, so proving Swift coverage requires querying known symbols or running a Cypher count ([mcp/resources.ts](https://github.com/abhigyanpatwari/GitNexus/blob/main/gitnexus/src/mcp/resources.ts)).

### Maturity, license, and the claims that could not be confirmed

GitNexus has very high traction and very high churn: **47.8k stars, 5.2k forks, 251 open issues, 2,178 commits**, and **988 npm versions in eight months** (first publish 6 February 2026; `latest` 1.6.12; five release candidates between 06:23 on 7 October and 11:20 on 8 October 2026) **[Source]** ([GitHub](https://github.com/abhigyanpatwari/GitNexus); [npm registry](https://registry.npmjs.org/gitnexus)). The license is **PolyForm Noncommercial 1.0.0**, with "commercial licensing or enterprise inquiries" routed to founders@akonlabs.com ([LICENSE](https://github.com/abhigyanpatwari/GitNexus/blob/main/LICENSE); [README](https://github.com/abhigyanpatwari/GitNexus/blob/main/README.md)). For a commercial iOS shop this is a hard gate: production use requires a paid license, and even an internal evaluation should be cleared with legal first. Claims that could not be verified against a primary source include YC S26 backing and 65,000 weekly npm downloads ([stork.ai](https://www.stork.ai/en/gitnexus-akon-labs), snippet), a "51% cheaper" coding-agent benchmark on Product Hunt (no method, model or dataset traceable) ([Product Hunt](https://producthunt.com/products/gitnexus-akon-labs)), and a third-party report that part of the star count was inflated by a crypto impersonation and that LangWatch switched to the MIT-licensed CodeGraphContext over the license ([Pebblous report](https://blog.pebblous.ai/report/gitnexus-production-report-2026/en/), snippet). The practical consequence of the release cadence is that any evaluation must pin an exact version for its whole duration.

### The independent evidence for code-graph tools is thin, mixed, and Swift-free

GitNexus ships a SWE-bench harness comparing a grep-only baseline against native graph tools, but its results directory is gitignored and no numbers appear in the repository ([eval/README.md](https://github.com/abhigyanpatwari/GitNexus/blob/main/eval/README.md)). The three independent data points point the same way: fewer tool calls and less wall time, with token and resolve-rate effects small, mixed, or vendor-reported. GitLab's Knowledge Graph study on SWE-Bench Lite (23 issues, Claude Sonnet 4, 11 runs per configuration because "Anthropic's API has no per-call seed") found the graph-only agent "made about 21% fewer tool calls," "took about 20% less time per issue," but "used about 5% more tokens than baseline," resolved between 5 and 7 of 23 issues across runs, and — the most important caution — "baseline + GKG perform[ed] worse than expected," with Sonnet "rarely re-index[ing], so it often read full files instead of using the graph, possibly due to stale data concerns" ([GitLab GKG issue #224](https://gitlab.com/gitlab-org/rust/knowledge-graph/-/issues/224)). An arXiv study of tree-sitter knowledge graphs via MCP reports the graph agent reaching "90% of the Explorer Agent's quality score while consuming an order of magnitude fewer tokens," graded by its own first author ([arXiv 2603.27277](https://arxiv.org/pdf/2603.27277), snippet). Sourcegraph's vendor-run CodeScaleBench claims Precision@5 rising from 0.140 to 0.478 and ~30% token savings ([Sourcegraph blog](https://sourcegraph.com/blog/codescalebench-testing-coding-agents-on-large-codebases-and-multi-repo-software-engineering-tasks), snippet). None covers Swift, Objective-C or Xcode projects. Anthropic's own position, reported secondhand, is that early Claude Code tried embedding retrieval and "landed on just agentic search," with the evidence "some internal benchmarks also, but mostly vibes" ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/), snippet); the official docs recommend LSP plugins for typed languages because "A single 'go to definition' call replaces what might otherwise be a grep followed by reading multiple candidate files" and note that CLI tools are "more context-efficient than MCP servers because they don't add any per-tool listing" ([Manage costs](https://code.claude.com/docs/en/costs)).

For Swift the compiler-backed alternatives are the correct comparison baseline, not "no tooling." Anthropic's `swift-lsp` plugin gives exact definitions, references, call hierarchies and post-edit diagnostics, but needs SwiftPM or, for `.xcodeproj`, a Build Server Protocol shim such as `xcode-build-server config -project X.xcodeproj -scheme Y` (which writes `buildServer.json` and goes stale until Xcode rebuilds) or the newer `sourcekit-xcode-bsp` ([Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence); [xcode-build-server](https://github.com/SolaWing/xcode-build-server)). Serena wraps sourcekit-lsp with 5–15 s initialization retries and lists Swift but no Objective-C ([Serena sourcekit_lsp.py](https://raw.githubusercontent.com/oraios/serena/main/src/solidlsp/language_servers/sourcekit_lsp.py)); IndexStoreDB-based servers (SwiftLens, Xcode Index MCP) are exact but macOS-and-Xcode bound ([indexstore-db](https://github.com/swiftlang/indexstore-db)). GitNexus's distinct value is graph-level `impact`/`trace`/`detect_changes`, Objective-C coverage, and cross-platform, build-free indexing — none of which the LSP route provides — at the price of heuristic edges and a commercial license.

### A rigorous method for deciding whether it, or any code-intelligence tool, helps

The method below is a proposal **[Inference]** that borrows its controls from GitNexus's own `workflow_bench` design ("Every arm runs in a fresh detached git worktree … Token savings on a failed task are flagged, not celebrated") and the GitLab study's caveats, and its measurement mechanics from Claude Code's documented headless output and telemetry ([workflow_bench README](https://github.com/abhigyanpatwari/GitNexus/blob/main/eval/workflow_bench/README.md); [Headless](https://code.claude.com/docs/en/headless); [Monitoring usage](https://code.claude.com/docs/en/monitoring-usage)). It starts with a gate that most teams skip: proving the tool parsed Swift at all.

```bash
# 0. Pre-flight gate — fail here and stop
npm i -g gitnexus@1.6.12                         # pin; never @latest during the study
claude --version; node --version; xcodebuild -version; git rev-parse HEAD   # record all four
cd "$REPO" && gitnexus analyze 2> /tmp/gn.stderr
grep -Ei 'tree-sitter-swift.*unavailable|SKIP_OPTIONAL_GRAMMARS' /tmp/gn.stderr && { echo "FAIL: Swift not parsed"; exit 1; }
git ls-files | grep -E '\.(swift|m|mm|h)$' | wc -l   # expected source-file count
gitnexus status --json                              # compare files/symbols/processes to the count above
# property names come from the gitnexus://repo/<name>/schema resource; adjust before running
gitnexus cypher "MATCH (n) WHERE n.filePath ENDS WITH '.swift' RETURN count(n)"
gitnexus context AppDelegate                        # must be a class node with file:line, not a file node
gitnexus impact 'PlayerViewModel.configure'         # compare callers against Xcode > Find Call Hierarchy
```

The gate then spot-checks ten Swift and five Objective-C symbols (the `@main` App, a `UIViewController` subclass, a SwiftUI `View`, a protocol with an extension default, a category method with a multi-part selector), requires correct file and line plus caller precision of at least 0.8 against a hand-verified list, confirms on an `.xcodeproj` without `Package.swift` that app-target and extension-target files resolve to separate modules (a method defined in both must not cross-link, the `swift-xcode-targets` fixture pattern), confirms a declaration inside `#if os(tvOS)` and an override like `didUpdateFocus(in:with:)` are findable, and times an incremental re-index after a commit so the PostToolUse staleness loop can be budgeted.

The arms are paired on the same task, base commit, model, effort, permission mode and CLAUDE.md text. A0 `baseline_nomcp` is `claude --bare -p` with Grep/Glob/Read/Bash only and the shared CLAUDE.md passed via `--append-system-prompt`; A1 `lsp` adds the `swift-lsp` plugin via `--plugin-dir` with a fresh `buildServer.json` (verify the "Found N new diagnostic issues" line appears once); A2 `gitnexus_tools` adds only the MCP server via `--mcp-config` with skills, hooks and the CLAUDE.md block disabled (`gitnexus analyze --skip-skills --skip-agents-md`); A3 `gitnexus_full` is the vendor's "Full" configuration with hooks and skills; A4 `lsp+gitnexus_full` tests the GitLab finding that stacking can hurt. Each task-arm pair runs at least five times (GitLab used eleven) in a fresh `git worktree` with `.gitnexus/` deleted and re-analyzed per worktree, with run order randomized and arms interleaved to spread API variance, capped by `--max-turns` and `--max-budget-usd`:

```bash
claude --bare -p "$(cat tasks/$TASK/prompt.md)" \
  --model claude-sonnet-5 --effort high --permission-mode acceptEdits \
  --allowedTools "Read,Grep,Glob,Edit,Write,Bash(xcodebuild *),Bash(swift *),Bash(git *)" \
  --append-system-prompt "$(cat CLAUDE.shared.md)" \
  ${MCP_CONFIG:+--mcp-config "$MCP_CONFIG"} ${PLUGIN_DIR:+--plugin-dir "$PLUGIN_DIR"} \
  --max-turns 60 --max-budget-usd 10 \
  --output-format stream-json --verbose > "runs/$TASK/$ARM/$RUN.jsonl"
# the last line is the `result` event with cost, duration, num_turns and session_id
```

The task set must be built by the team, because no iOS benchmark exists to borrow from: eight to twelve tasks labelled trivial, investigation, cross-module and UI+network, mixing Swift-only, Objective-C-only and mixed code. Good candidates are a crash triage from a symbolicated log (hidden oracle: a reproducing unit test now passes), a cross-module rename spanning app target, widget extension and test bundle (oracle: `build-for-testing` succeeds for all targets and hidden tests pass; files touched versus ground truth gives impact precision and recall), a SwiftUI screen backed by a new injected network client (oracle: hidden view-model and `URLProtocol`-stubbed tests), a tvOS focus regression (oracle: hidden focus assertions in a tvOS-simulator XCTest), an Objective-C nullability or selector mismatch, a pure call-site enumeration ("list all call sites of X across targets," oracle: exact set), and a deletion-impact question (oracle: compile result). Hidden tests live outside the worktree the agent sees.

Metrics per run come from the `stream-json` result and OpenTelemetry. Correctness: `resolved` (hidden oracle passes), first `xcodebuild` success, blind human-review defects, and hallucinated-API count via compiler errors. Efficiency: `total_cost_usd`, input/output/cache tokens by model from `claude_code.token.usage`, `num_turns`, wall and API duration, tool-call distribution from `claude_code.tool_result.tool_name`, GitNexus's cost share from `claude_code.cost.usage{mcp_server.name="gitnexus"}`, bytes injected by hooks as the `tool_result_size_bytes`/`tool_input_size_bytes` delta between A2 and A3, and time to first correct build. Process: how many GitNexus tool calls actually occurred and whether `impact`/`context` output was used (GitLab found the model often bypassed the graph), re-index count, and diff churn as an over-engineering proxy. Report medians and interquartile ranges per task per arm, and pre-register the decision rule before the first run — for example, adopt if resolve rate improves by at least ten points on cross-module tasks with no cost increase over 20%, or cost drops at least 25% with no resolve-rate loss. Red flags that should stop or discount the study are the Swift-grammar warning or a near-zero Swift node count (the index is parsing only build scripts and JSON), `impact` returning unrelated same-name members (the #3426 pattern, measured as false-caller rate on `configure`/`start`/`update`), stale-index warnings mid-task, Grep latency inflated by the 10-second hook (compare `tool_result.duration_ms` between A0 and A3), `cacheCreation` token spikes signalling context bloat, GitNexus tools listed but called zero or one times while cost rises, resolve rates varying by more than two tasks across repeats, and any use without an Akon Labs license. The same gate applies to any other tool: for LSP-based tools confirm `buildServer.json` points at a current build root and that find-references on a cross-target symbol returns hits from every target; for IndexStoreDB tools confirm the index store was built with `-index-store-path` after the latest commit.

## Conclusion

The most useful reframing from this research is that "elite usage" of Claude Code on Apple platforms is almost entirely an infrastructure question, not a prompting question. The engineers and teams getting outsized results spent their effort on the loop (fast, filtered, targeted builds; simulator and screenshot access; hidden tests and adversarial reviews) and on the governance layer that makes delegation safe (short context files that only say what cannot be inferred, hooks and permissions for the things that must never happen, every architectural boundary enforced twice). Once those exist, the prompts become short and boring, which is the point: Shopify's agents got "the existing app serves as the spec," Duolingo's got "a file to test and the rules that stop known failure modes," and the official templates amount to "here is the file, here is the example, here is the check." The corollary for a team evaluating adoption is that the first month should be judged by whether the loop closes — can Claude build, test, launch and look at the app without a human in the middle, including on an Apple TV simulator — rather than by lines of code produced.

The GitNexus question resolves into the same frame. The tool is real, actively developed and now Swift-aware, but its edges are heuristic, its license is non-commercial, and the field's own evidence says graph tools reliably cut tool calls and time while their effect on correctness and tokens depends on the agent actually using the graph and on whether stacking it with other tools helps or hurts. A team that has built the baseline arm this report describes — bare Claude Code plus the `swift-lsp` plugin, a hidden test set and telemetry — can answer the question in two weeks on its own repository, and will have gained the measurement harness it needs for every future tool decision, which is a better return than any vendor benchmark could offer.
